# 임베딩 작업 큐와 청크 기반 RAG 검색

> 개인 프로젝트 iNote의 "내 글을 LLM이 검색해 답하는 기능"에서, **글 전체가 검색되도록** 임베딩 파이프라인과 검색 방식을 바꾼 작업.
> 상태: **개발 환경에서 구현·검증 완료, 운영 미반영**(운영 AI DB에 SQL 적용 전). 이 문서는 학습용이 아니라 기록용이다.

## 1. 한 줄 요약
글을 앞 1,500자에서 잘라 벡터 하나로 임베딩하던 방식 때문에 글 뒷부분 내용은 검색되지 않았다. 글 전체를 문단 기반 조각(청크)으로 나눠 임베딩하고, 무거운 임베딩 모델 서버가 닿지 않아도 요청을 잃지 않는 작업 큐와 로컬 워커를 추가했다.

- **기간**: 2026-11-03 ~ 04 (이 항목의 범위). 앞선 10월에 임베딩 서비스와 글 벡터 저장·유사 글 조회가 만들어져 있었다.
- **역할**: 설계 결정 승인과 방향 제시(본인) + 구현·테스트 작성(Claude Code와 협업). 구분은 4절.
- **레포**: `inote-ai`(FastAPI, 구현 대부분), `inote-embedder`(KURE-v1 임베딩 서버), `inote-server`(NestJS, 글 저장 시 호출), `inote`(문서)
- **기술**: Python 3.9·FastAPI·psycopg3·PostgreSQL(pgvector)·KURE-v1(한국어 임베딩, 1024차원)·Docker·unittest

## 1-1. 전체 동작 흐름
세부 설명 전에 "글이 저장되고, 검색되고, 답이 되기까지"를 먼저 본다. 아래 흐름은 모두 현재 코드 기준이다.

**구성 요소**
| 구성 요소 | 하는 일 | 도는 곳 |
|---|---|---|
| `inote-server` (BE) | 글 원문(HTML) 보관, 글 저장 때 `inote-ai` 호출, 공개 글 id 목록·공개 글 상세 제공 — **공개 여부는 항상 BE가 판단** | Render |
| `inote-ai` | 임베딩 API, 작업 큐 관리, 조각 검색, 글 목록 채팅(LLM 답변) | Vercel |
| `inote-embedder` | 텍스트 → 벡터(KURE-v1). 상태 없음, DB 모름 | 로컬 Docker (운영 호스팅 미정) |
| 워커 | 큐의 대기 작업을 한 건씩 처리 | 로컬 프로세스 (임베딩 서버 옆) |
| AI DB (PostgreSQL + pgvector) | 아래 저장소 표 참고 | 운영 Supabase / 개발 Docker |

**AI DB에 저장되는 것**
| 테이블 | 내용 | 글 본문 |
|---|---|---|
| `post_embedding` | 글 벡터 1개 (제목 + 본문 앞 1,500자) | 없음 |
| `post_chunk_embedding` | 조각 벡터 + 글 안에서의 위치 + 해시 | **없음** (위치·해시만) |
| `embedding_job` | 임베딩 대기 작업 | **처리 전까지만** 임시 저장, 완료하면 삭제 |

### A. 글 저장 → 임베딩
```
글 저장
  FE ──▶ inote-server : 글 저장 (원문 HTML은 BE DB에 보관)
  inote-server ──▶ inote-ai : PUT /embeddings/posts/{id}  (제목 + HTML 본문)
                      · 응답을 기다리지 않고, 실패해도 글 저장은 성공한다

inote-ai 처리
  1. HTML → 텍스트로 바꾸고 조각(약 800자, 겹침 100자)으로 나눈다
  2. 저장된 상태(모델·해시)와 비교해, 바뀐 것만 다시 만들 대상으로 정한다
       └ 바뀐 게 없으면 "unchanged"로 끝 (임베딩 서버를 부르지 않음)
  3. 임베딩 서버(KURE)에 텍스트를 보낸다 (한 번에 16개씩)
       ├ 성공 ─────────────▶ 4번으로
       └ 닿지 못함 / 오류 ──▶ embedding_job에 pending으로 저장, 202 "queued"로 응답 ──▶ [B]
  4. 이 글의 대기 작업을 먼저 지운다 (처리 중인 워커의 오래된 결과가 덮어쓰지 못하게)
  5. 글 벡터 + 조각 벡터를 한 트랜잭션으로 저장한다 ──▶ 200 "embedded"
       (조각은 이전 것을 모두 지우고 새로 넣는다. 도중에 실패하면 전부 되돌아간다)

글 삭제 시: DELETE로 글 벡터·조각·대기 작업을 함께 지운다.
기존 글: 백필 스크립트가 글마다 위 PUT을 호출해 채운다 (같은 내용이면 건너뜀).
```

### B. 큐 처리 (로컬 워커)
```
python -m scripts.embedding_worker  (임베딩 서버와 같은 곳에서 실행)

반복:
  1. embedding_job에서 pending 작업 하나를 잠그고 가져온다 → processing
       (FOR UPDATE SKIP LOCKED: 워커가 둘이어도 같은 작업을 가져가지 않는다)
  2. A의 1~3과 같은 규칙으로 임베딩한다
       ├ 임베딩 서버에 닿지 못함 ─▶ 작업을 pending으로 되돌리고(시도 횟수 안 셈) 멈춘다
       ├ 응답은 왔는데 오류 ──────▶ 시도 횟수 +1, 5회가 넘으면 failed
       │                            (연속 3건 실패하면 서비스 문제로 보고 멈춘다)
       └ 성공 ───────────────────▶ 벡터 저장 + done + 본문 삭제를 한 트랜잭션으로
              └ 그 사이 글이 다시 저장되어 version이 달라졌으면 이번 결과는 버린다
  (처리 중에 멈춘 작업은 일정 시간 뒤 다시 가져간다)
```

### C. 글 찾기 (질문 → 답변)
```
글 목록 채팅에서 질문
  FE ──▶ inote-ai : 질문

  1. inote-server에서 공개 글 id 목록을 받는다            (공개 여부 판정은 BE)
  2. 질문을 임베딩 서버로 벡터로 바꾼다
  3. 후보 id 안에서 가까운 조각 12개를 찾는다
       + 조각이 아직 없는 글은 글 벡터로 보충한다           (롤아웃 중에도 검색에서 빠지지 않게)
  4. 글 단위로 합친다 (글 점수 = 가장 가까운 조각 점수) → 기준 점수로 거르고 상위 3편
       └ 기준을 못 넘으면 "관련 글 없음" ──▶ 일반 답변으로 넘어간다
  5. inote-server에서 그 글의 원문을 가져온다           (공개 조회 API, 비공개면 404)
  6. 근거 텍스트를 만든다: 찾은 조각 + 앞뒤 이웃 조각을 원문에서 저장된 위치로 다시 잘라 낸다 (글당 최대 3,000자)
       └ 저장된 해시와 다르면(글이 그 사이에 바뀜) 위치를 믿지 않고 앞 1,500자로 대신한다
  7. 근거를 LLM(Groq)에 주고, 출처 번호와 함께 답변을 스트리밍한다
  FE ◀── 답변 + 출처(글 id·제목·카테고리·점수)
```

## 2. 배경과 문제
- 글을 저장하면 제목+본문 **앞 1,500자**만 임베딩해 글당 벡터 1개를 저장했다. 속도를 이유로 둔 상한이었다.
- 운영 공개 글 56편(2026-11-03 읽기 전용 집계) 중 **29편(52%)이 1,500자 초과**, 본문 길이 중앙값 1,769자·최대 9,507자(HTML 태그 제외). 뒷부분 내용으로 질문하면 해당 글이 검색되지 않는다.
- 임베딩 모델(KURE-v1)은 메모리를 약 0.9GB 쓰고(로컬 Docker 측정) 첫 기동에 약 2분이 걸려, 운영 API(Vercel 서버리스)에 올릴 수 없고 무료 호스팅 후보(Render 무료 512MB 등)에도 맞지 않았다. 그래서 운영 서버가 임베딩 서버에 못 닿는 상황이 기본이다.

## 3. 목표
1. 모든 공개 글의 **전체 내용**이 검색되게 한다.
2. 임베딩 서버가 꺼져 있어도 글 저장 요청이 사라지지 않게 하고, 서버가 있는 곳(로컬)에서 한 건씩 처리한다.
3. 비공개 글이 새어 나가지 않게 하고, 운영 데이터는 건드리지 않는다.

## 4. 설계 결정과 이유
| 결정 | 이유 | 정한 사람 |
|---|---|---|
| 글 하나를 청크 여러 개로 임베딩 (글 단위 → 조각 단위 검색) | 1,500자 제한을 풀지 않고도 뒷부분이 검색됨. 긴 글을 한 벡터로 뭉뚱그리면 주제가 흐려짐 | 본인 (여러 안 중 선택) |
| 임베딩 서버(KURE)를 API 서버와 분리 유지 | 메모리·기동 시간·CPU 사용 성격이 달라 한 프로세스에 묶으면 채팅 API까지 느려짐. 상태 없는 서버라 호스팅 이전이 쉬움 | 본인 |
| 요청을 순서대로 큐에 넣고 하나씩 처리 | 서버 CPU 한계, 서버가 닿지 않을 때 요청 보존 | 본인 아이디어 → 구조는 협업 |
| 큐 = DB 테이블, 워커 = 임베딩 서버 옆 별도 프로세스 | 서버가 꺼져도 작업이 남음. 벡터 저장·해시 규칙이 이미 `inote-ai`에 있어 중복이 없음. (큐를 임베딩 서버에 두면 그 서버가 DB 접속 정보를 가져야 해서 버림) | 협업 후 본인 승인 |
| 청크 본문은 DB에 저장하지 않고 위치(offset)+해시만 저장 | 삭제한 글의 내용이 AI DB에 남지 않음. 보여 줄 때 원문에서 다시 잘라 냄 | 본인 승인 |
| 공개 글만 검색 (요청자 검증 전까지) | 현재 AI 서버가 요청의 user_id를 그대로 신뢰하는 문제가 있어 비공개 글 검색은 보류 | 기존 결정 |
| 개발 DB에서 먼저 검증, 운영은 읽기 전용 | 운영 데이터 보호 | 본인 |

## 5. 구현 포인트
**작업 큐와 워커** (`inote-ai`: `embedding_jobs.py`, `embedding_worker.py`, `scripts/embedding_worker.py`)
- 글 하나당 작업 하나(upsert). 상태 `pending/processing/done/failed`, 시도 횟수, 버전.
- `FOR UPDATE SKIP LOCKED`로 워커가 둘이어도 같은 작업을 동시에 가져가지 않는다(두 세션 동시 실행으로 확인).
- 벡터 저장과 `done` 처리를 **한 트랜잭션**으로 하고, 그 사이 글이 다시 저장되어 버전이 바뀌었으면 오래된 결과를 버린다(낙관적 확인).
- 임베딩 서버에 **닿지 못한 경우**(시도 횟수를 세지 않고 멈춤)와 **응답은 왔지만 오류**(횟수를 세고 상한 도달 시 `failed`)를 구분해, 서버가 꺼진 동안 작업이 소모되지 않고 한 작업이 큐를 막지도 않는다. 연속 3건 실패하면 서비스 문제로 보고 멈춘다(서킷 브레이커).
- 처리 중 멈춘 작업은 일정 시간 뒤 다시 가져간다. 로그에는 글 id만 남긴다.
- 워커 CLI는 개발 DB(로컬 호스트 + DB 이름이 `_dev`로 끝남)가 아니면 명시적 옵션 없이는 실행을 거절한다.
- 경쟁 상태 방지: 저장 API가 최신 벡터를 쓰기 **전에** 그 글의 대기 작업을 지워, 처리 중이던 워커의 오래된 벡터가 최신 벡터를 덮어쓰지 못한다.

**청커** (`chunking.py`)
- 문단 → 문장 → 공백 → 글자 수 순으로 나눠 문단·문장을 최대한 쪼개지 않는다. 겹침 100자, 끝의 짧은 조각은 앞에 붙인다.
- 청크가 원문의 연속 조각이라 `text[start:end]`가 청크 그대로 — offset만 저장해도 복원된다. 같은 입력은 항상 같은 결과(해시 비교 전제).
- 크기는 추측이 아니라 **측정**으로 정했다(6절).

**저장과 검색**
- 글 벡터와 조각 벡터를 **한 트랜잭션**으로 저장(그 글의 조각을 지우고 새로 삽입). 임베딩 묶음 중 하나라도 실패하면 아무것도 저장하지 않고 큐에 남긴다. 글 벡터와 조각은 해시를 따로 비교해 바뀐 쪽만 다시 만든다.
- 검색은 후보 글 id(서버가 정한 공개 글 목록) **안의 조각만** 대상으로 한다. 글 점수는 가장 가까운 조각 점수, 근거 텍스트는 찾은 조각과 앞뒤 이웃 조각을 원문에서 잘라 만든다.
- 글이 그 사이에 바뀌어 저장된 해시와 다르면 어긋난 위치를 쓰지 않고 앞부분 텍스트로 대신한다. 조각이 아직 없는 글은 기존 글 벡터로 보충해 롤아웃 중에도 검색에서 빠지지 않는다.

## 6. 결과와 측정
모든 수치는 **로컬 개발 환경**(운영 공개 글을 읽기 전용으로 가져와 로컬 임베딩 서버·개발 DB에 저장)에서 측정했다.

| 항목 | 값 | 비고 |
|---|---|---|
| 한국어 글자 수 / 토큰 수 | 약 2.05자 = 1토큰 (글별 1.76~2.43) | 공개 글 57편 117,775자 = 57,365토큰, KURE 토크나이저 |
| 모델 최대 입력 | 8,192토큰 | 가장 긴 글(9,355자)도 4,085토큰 → 1,500자 제한은 모델 한도가 아니라 속도 때문이었음을 확인 |
| 청크 크기 | 목표 800자 ≈ 390토큰, 최대 1,000자 | 위 비율로 결정 |
| 생성된 조각 | 59편 → **197개**, 글당 최소 1·중앙 3·최대 14, 조각 길이 중앙 766자·최대 800자 | 100자 미만 조각 4개는 모두 짧아서 조각이 1개뿐인 글 |
| 임베딩 소요 | 조각 포함 59편 396초, 글 벡터만 57편 155초 | 로컬 CPU, 글당 1~27초 |
| 뒷부분 검색 (1차, 쉬운 질의) | 3,000자 이상 글 17편에서 80% 지점 문장 150자로 검색 → **1위 적중 13/17 → 17/17** | 최악 사례 34위 → 1위 |
| 바꿔 쓴 질문 평가 (2차) | 질문 18개(정답 있음 12·관련 글 없음 6). 정답 있는 질문에서 **Recall@1 0.58 → 0.92, Recall@3 0.83 → 0.92, MRR 0.73 → 0.93** (글 벡터 → 조각 검색) | 못 찾은 1개는 표현이 많이 달라 6위 |
| 기준 점수 | 관련 없는 질문의 오탐 **50% → 0%** (기준 0.5 → 0.59), 정답을 보여준 비율은 92% 유지. margin은 0.09 → 0.05 | 오탐 0%·정답 유지 구간 0.57~0.61의 중앙. 정답 외 글 평균 0.58편 → 0.33편(기준 0.60 기준) |

**측정의 한계 (이력서에 쓸 때 반드시 함께 적을 것)**
- 1차 비교는 본문을 그대로 베낀 문장을 질의로 쓴 **쉬운 질의**이고 표본이 17편이다.
- 2차 평가의 질문 18개 중 **13개는 AI가 글을 읽고 작성**했다(정답 있는 12개 중 10개). 사용자가 직접 쓴 것은 5개(정답 있음 2·관련 없음 3)라 사용자 작성 질문만으로는 비교할 수 없고, AI가 본문을 보고 쓴 질문은 실제 사용자 질문보다 쉬울 수 있다.
- 관련 없는 질문이 6개뿐이고, 기준 점수는 같은 질문 세트로 정했다(튜닝에 쓰지 않은 질문으로 확인하지 못함). 그래서 0.59·0.05는 **잠정값**이다.

## 7. 테스트·품질
- 전체 **318개** 통과(개발 DB를 쓰는 실제 SQL 통합 테스트 포함). 큐·워커 단계에서는 239개였고, 평가 스크립트 테스트 17개가 포함된다.
- 지켜 주는 것: 도중 실패 시 글 벡터·조각이 일부만 바뀌지 않음(실제 DB 롤백), 후보 id 밖의 글이 검색되지 않음(실제 SQL), 원문이 바뀌면 어긋난 글자를 근거로 주지 않음, 글 하나에 조각이 몰려도 다른 글이 밀려나지 않음, 같은 입력은 같은 결과, 워커의 동시 실행·재시도·중단 처리.
- 레포 안에서 기능 단위로 나눈 커밋 5개로 정리(2절 근거 참고).

## 8. 어려웠던 점과 해결
- **원인 가설 교정**: "1,500자 제한이 모델 한도 때문"이라고 생각하기 쉬웠으나, 토크나이저로 재 보니 가장 긴 글도 모델 한도의 절반이었다. 그래서 문제를 "길이 한도"가 아니라 "뒷부분이 반영되지 않는 것"으로 다시 정의하고, 청크 크기를 측정값으로 정했다.
- **큐와 최신 벡터의 경쟁**: 워커가 처리하는 사이 같은 글이 다시 저장되면 오래된 벡터가 최신을 덮어쓸 수 있었다. 버전 확인과 "쓰기 전에 대기 작업 삭제" 순서로 막았다.
- **본문 미저장과 정합성**: 원문 없이 offset만 저장하면 글이 바뀔 때 위치가 어긋난다. 조각 해시를 같이 저장해 불일치를 감지하고 폴백하도록 했다.
- **운영 데이터 보호**: 운영 글을 읽어야 하는 작업이었으나, 읽기 전용 트랜잭션으로만 접근하고 출력에는 글 id·집계만 남기며, 쓰기는 개발 DB로만 했다.

## 9. 한계·후속
- **평가 세트가 작다.** 질문 18개(13개는 AI 작성, 관련 없는 질문 6개)로 기준 점수를 정했다(0.5 → 0.59, margin 0.09 → 0.05). 사용자가 직접 쓴 질문을 늘려 다시 재야 하고, 튜닝에 쓰지 않은 질문으로 확인해야 한다. 조각이 없는 글(백필 전)은 글 벡터 점수가 더 낮아 이 기준에 걸러질 수 있어, 백필 후에 적용한다.
- 운영 AI DB에 `embedding_job`·`post_chunk_embedding` SQL 적용과 기존 글 조각 백필이 남아 있다(운영 미반영).
- 긴 글은 저장 API가 길어져(로컬 최대 27초) 호출한 서버의 대기 한도(45초)에 가까워진다 — 큐 경로가 보완하나 호스팅 사양과 함께 봐야 한다.
- 비공개 글 검색은 요청자 검증 이후로 보류. 임베딩 서버의 운영 호스팅(Oracle Cloud Always Free 검토 중)은 미정.

## 10. 이력서 문장 후보
각 문장 뒤는 근거 절이다. **운영 반영 전**이므로 "구현·검증"으로 쓰고 "운영 중"이라고 쓰지 않는다.
1. 글을 앞 1,500자만 임베딩해 뒷부분이 검색되지 않던 RAG 검색을 문단 기반 청크(약 800자, 겹침 100자) 임베딩으로 개선하고, 개발 환경에서 바꿔 쓴 질문 12개 기준 Recall@1을 0.58에서 0.92로 높임 *(질문 18개 중 13개는 AI 작성, 표본 작음)* — 5·6절
2. 임베딩 모델(KURE-v1, 약 0.9GB)을 API 서버와 분리하고, PostgreSQL 작업 큐(`FOR UPDATE SKIP LOCKED`, 버전 기반 낙관적 확인, 벡터 저장·완료 단일 트랜잭션)와 로컬 워커로 비동기 임베딩을 설계·구현 — 4·5절
3. 청크 본문 대신 위치·해시만 저장하고 해시 불일치 시 폴백하도록 설계해 삭제된 글 내용 잔존을 막고 검색 정합성을 유지 — 4·5절
4. 토크나이저로 한국어 약 2.05자/토큰을 측정해 청크 크기를 결정하고, 실제 DB 통합 테스트를 포함한 318개 테스트로 검증 — 6·7절
5. Recall@k·MRR과 기준 점수 스윕(오탐/놓침) 평가 스크립트를 만들어 검색 기준 점수를 데이터로 조정(관련 없는 질문의 오탐 50% → 0%) *(잠정값, 표본 작음)* — 6절

## 11. 면접에서 설명할 포인트
- **왜 글자 수가 아니라 구조 기반으로 나눴나?** 문단·문장 경계를 먼저 지키고 글자 수는 상한으로만 쓴다. 완벽한 의미 경계는 아니라서, 겹침·이웃 조각 확장·제목 붙이기로 문맥 단절을 줄였고, 실제 품질은 평가 세트로 확인해야 한다고 인지하고 있다.
- **왜 큐를 DB 테이블로?** 서버가 꺼져도 남고 저장 요청과 워커가 같은 곳을 본다. 규모가 작아 별도 메시지 브로커는 과하다. 단점(폴링, 본문 임시 저장)과 완화(완료 시 본문 삭제)도 안다.
- **왜 청크 본문을 저장하지 않나?** 삭제·비공개 글의 내용이 두 번째 저장소에 남는 위험을 줄이려는 선택이고, 대신 원문 변경 감지(해시)와 폴백이 필요해졌다.
- **개선을 어떻게 증명했나, 무엇이 부족한가?** 바꿔 쓴 질문 12개에서 Recall@1 0.58 → 0.92이고, 관련 없는 질문으로 기준 점수의 오탐(50% → 0%)도 쟀다. 다만 질문의 대부분(13/18)을 AI가 글을 읽고 썼고 표본이 작아서, 사용자가 직접 쓴 질문을 늘려 다시 확인해야 한다.

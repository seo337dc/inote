# 채팅 답변을 세션별로 동시에 진행

> 개인 프로젝트 iNote의 채팅 위젯에서, 답변이 스트리밍되는 도중 다른 대화로 옮기면 새 대화 전송이 잠기던 한계를 **메시지·전송 상태를 세션별로 분리**해 없앤 작업.
> 상태: **FE PR #21 병합됨(2026-10-29), 가짜 AI 서버로 로컬 QA 완료. 실제 AI 서버(Groq)로는 미확인.** 이 문서는 학습용이 아니라 기록용이다.

## 1. 한 줄 요약
채팅 훅이 `messages`·`isSending`을 하나만 들고 있어, 답변이 오는 중 "새 대화"를 누르면 이전 대화가 멈춘 것처럼 보이고 새 대화 전송이 잠겼다. 상태를 세션별 맵으로 바꿔 이전 답변은 자기 대화에 계속 쌓이고 새 대화도 바로 보낼 수 있게 했다. 서버·큐 변경 없이 FE만 고쳤다.

- **기간**: 2026-10-28 검토 ~ 10-29 구현·병합
- **역할**: 큐 도입 여부 검토에서 "지금은 도입하지 않는다"를 정하고 표시 위치(대화 목록 행)를 지정한 것은 본인. 구현·테스트 작성은 Claude Code와 협업. 세부 구분은 4절. (누가 어느 결정을 했는지는 devlog 기준이며 일부는 확인 필요)
- **레포**: `inote`(FE, `apps/web/src/widgets/chat-dock`)
- **기술**: React 훅(`useState`·`useRef`), fetch 스트리밍(SSE 형태 `data:` 청크), Vitest + React Testing Library

## 1-1. 전체 동작 흐름
```
useChatMessages (훅 하나)
  messagesBySession : { [세션id | "guest"] : ChatMessage[] }   ← 세션별 메시지
  sendingKeys       : Set<세션id>   (화면용 state)
  sendingRef        : Set<세션id>   (이중 전송·비동기 콜백용 ref)

화면에 보이는 것 = 현재 활성 세션 키의 messages / isSending

전송:  sendMessage → 같은 세션이 이미 전송 중이면 무시
        └ 아니면 그 세션 키를 sendingRef/sendingKeys에 추가 → /chat/stream 스트림
          조각이 올 때마다 "그 세션 키"의 메시지에만 append (화면에 있든 없든)
          끝나면 세션 키만 제거
세션 전환: startNewSession은 세션 id만 바꾸고 이전 세션의 메시지는 그대로 둔다
이력 로드: 전환한 세션이 전송 중이면 서버 이력으로 덮어쓰지 않는다
```

## 2. 배경과 문제
- 코드로 읽은 원인(2026-10-28 검토 기록, 지금은 삭제돼 출처 절 참고): 답변 도중 "새 대화"를 누르면 `messages`는 비워지지만 `isSending`·`sendingRef`는 그대로라, 이전 스트림이 끝날 때까지 새 대화 전송이 잠기고 로딩 표시도 없었다. 이전 답변 글자는 메시지 id가 없어 화면에서 버려졌지만 서버 연결·생성은 끝까지 갔다.
- 사용자 입장에서는 "대화 A가 멈췄고, 새 대화는 아직 못 보낸다"로 보였다.
- 서버(`inote-ai`)는 Vercel 서버리스 위에서 돌고, 답변은 스트림이 끝난 뒤에 저장된다(이 사실은 훅 주석·devlog 기준).

## 3. 목표
1. 답변이 진행 중이어도 다른 대화로 옮겨 새 질문을 보낼 수 있다.
2. 이전 답변은 끊기지 않고 자기 대화에 계속 쌓이며, 돌아오면 이어서 보인다.
3. 같은 대화 안의 이중 전송 방지 등 기존 보호는 유지한다.

## 4. 설계 결정과 이유
검토한 선택지(2026-10-28, 삭제된 `feature-backlog-and-direction.md`, 결과는 `docs/todo/backlog.md` 9절):

| 안 | 판단 | 이유 |
|---|---|---|
| (가) MQ/큐에 넣어 두었다가 이전 답변이 끝나면 다음 질문 진행 | 도입하지 않음 | 같은 대화 안 "미리 입력"에는 맞지만, 새 대화로 옮긴 경우 보낸 질문이 보류돼 어색하다. 브라우저 배열 하나로 충분해 서버 MQ는 불필요 |
| (나) 서버에서 생성과 연결을 분리해 백그라운드로 계속 완성 | 도입하지 않음 | 큐·워커가 필요한데 `inote-ai`가 Vercel(서버리스)이라 계속 떠 있는 워커를 둘 수 없다. 호스팅을 늘려야 하고, 답변 한 번이 수 초라 이득에 비해 운영 비용이 크다 |
| (다) AbortController로 이전 답변 중단 | 검토 단계 제안 | 단순하지만 이전 답변이 사라지고, 중단된 답을 서버가 어떻게 저장하는지 미확인 |
| **(라) 세션마다 메시지·전송 상태를 따로 들고 동시 진행 (채택)** | 채택 | 큐 없이 잠금이 풀리고, 서버 변경이 없다. 상태 구조를 바꾸는 큰 리팩터라 원래 ADR 0006(세션 구조 개편) 때 재검토하자는 제안이었으나, 이번에 FE 훅 범위에서 먼저 구현 |

- **서버리스 제약으로 이번에 못 하는 것**: 새로고침·탭 닫기 후 진행 중 답변 이어받기, 백그라운드 재시도 큐. `inote-ai`를 상시 서버로 옮기거나 별도 워커를 둘 때 다시 검토한다.
- **범위 결정**: FE만 수정. 세션 선택 로직은 ADR 0006이 바꿀 예정이라 건드리지 않았다. "답변 중" 표시는 대화 목록 행에만 달았다(위치는 사용자가 스크린샷으로 지정, 기록 버튼에는 달지 않음).
- MQ는 "응답을 기다릴 필요가 없는 진짜 비동기 작업"(예: 글 저장 후 임베딩 생성)이 생길 때 다시 꺼내기로 기록했다.

## 5. 구현 포인트
`apps/web/src/widgets/chat-dock/model/useChatMessages.ts`
- 메시지를 `messagesBySession`으로 보관하고(`:33`), 화면에는 활성 세션 키 것만 노출(`:39-41`). 로그인 안 한 게스트는 세션 id가 없어 `"guest"` 키를 쓴다(`:15`).
- 전송 상태는 두 벌: 화면용 `sendingKeys`(state)와 같은 틱 이중 클릭·비동기 콜백의 최신 값 확인용 `sendingRef`(ref `Set`) (`:35-37`). 같은 세션이면 전송을 무시하고 다른 세션은 막지 않는다(`:182-197`).
- 스트림 조각을 항상 **전송 시작 시점의 세션 키**로 append한다(`appendAssistantText(key, …)`, `:260`, `:271-275`). 그래서 사용자가 다른 대화를 보고 있어도 이전 답이 자기 대화에 쌓인다.
- 이력 로드 경합 처리: 서버는 답변이 끝나야 저장하므로, 진행 중인 세션을 서버 이력으로 덮어쓰면 화면의 답이 사라진다. 전환 직후와 이력 응답을 기다리는 사이 양쪽에서 `sendingRef`를 확인해 덮어쓰기를 막는다(`:140-143`, `:157`).
- `startNewSession`은 세션 id만 바꾸고 메시지를 지우지 않는다(`:162-167`).
- 부가: 진행 중 세션 id를 `answeringSessionIds`로 내보내(`:303`) 대화 목록 행에 붉은 "답변 중" 점을 표시(`ChatSessionPanel.tsx`). 독서 채팅 훅은 세션이 없어 빈 값을 돌려준다(두 훅 반환 타입 맞춤).

## 7. 어려웠던 점과 해결
- **이력 로드가 진행 중 답을 덮어쓰는 경합**: 세션 전환 시 서버 이력을 불러오면, 아직 저장되지 않은(서버는 답이 끝나야 저장) 서버 이력이 화면의 진행 중 답을 빈 값으로 덮는다. 요청 시점과 응답 시점 두 곳에서 전송 중 여부를 확인해 막았다.
- **state와 ref의 역할 분리**: 렌더 값(state)은 비동기 콜백에서 오래된 값을 볼 수 있어, 이중 전송 방지·덮어쓰기 방지 판단은 ref `Set`으로 하고 화면 표시는 state로 복제했다.
- **"멈춘 것 같다" 인상**: QA 중 다른 대화에 있는 동안 진행이 보이지 않아 멈춘 듯하다는 인상이 한 번 있었다(서버 로그로는 멈추지 않음). 원인을 "진행 표시 부재"로 추정해 대화 목록에 붉은 점을 추가했다(추정이며 실제 원인 단정은 아님).

## 8. 한계·후속
- **새로고침·탭 닫기 시 진행 중이던 답은 끊긴다.** 서버리스(Vercel) 제약으로, 서버가 생성을 연결과 분리해 들고 있지 못한다. 서버가 질문만 저장하고 답은 저장하지 않을 수 있다(QA 6-3, 결과 미기록).
- **실제 AI 서버(Groq)로 확인하지 못했다.** 가짜 서버는 실제 청크 모양·지연과 다르고, 서버의 답변 저장 시점도 코드 독해로 흉내 냈다. 운영 서버로 1회 확인 필요.
- 스트림 파싱의 `JSON.parse`에 예외 처리가 없다(`useChatMessages.ts:259`). 도중에 서버가 끊기거나 잘못된 청크가 오면 어떻게 되는지 미확인.
- 대화 목록이 닫혀 있으면 "답변 중" 점이 보이지 않는다(시계 버튼에는 달지 않기로 함).
- 대화 3개 이상 동시 진행 시 Groq 요청 제한(429) 동작은 미확인.
- 세션 선택 로직 개편은 ADR 0006에서 다룰 예정.

## 9. 이력서 문장 후보
1. 채팅 답변이 스트리밍되는 도중 다른 대화로 옮기면 새 대화 전송이 잠기던 문제를, 메시지·전송 상태를 세션별로 분리해 이전 답변은 계속 진행되고 새 대화도 바로 보낼 수 있게 개선 *(FE만 수정, 가짜 AI 서버로 로컬 확인)* — 2·5·6절
2. 메시지 큐 도입안과 세션별 상태 분리안을 비교해, 서버리스(Vercel) 환경에서 상시 워커를 둘 수 없다는 제약과 운영 비용을 근거로 큐 없이 클라이언트 상태 설계로 해결 — 4절
3. 서버가 답변 완료 후에만 대화를 저장하는 점 때문에 생기는 "이력 로드가 진행 중 답을 덮어쓰는" 경합을 ref 기반 전송 상태 확인으로 방지하고, 훅 테스트 5개·패널 테스트 3개로 보호 — 5·6·7절

## 10. 면접에서 설명할 포인트
- **왜 MQ를 안 썼나?** 같은 대화 안 대기는 브라우저 배열로 충분하고, 서버에서 백그라운드로 완성하려면 연결과 생성을 분리하는 상시 워커가 필요한데 서버리스라 불가했다. 답변 한 번이 수 초라 운영 비용 대비 이득이 작다고 판단했고, 이 결정을 문서로 남겼다.
- **state와 ref를 왜 둘 다 썼나?** 화면 갱신은 state, 같은 틱 이중 클릭·비동기 콜백의 최신 값 판단은 ref.
- **한계는?** 새로고침하면 진행 중 답이 끊긴다. 해결하려면 서버 쪽 생성 분리(상시 서버·워커)가 필요해 호스팅 결정과 묶인다. 실제 Groq로는 확인하지 않았다.

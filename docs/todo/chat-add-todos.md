# 할 일 — 채팅에서 할 일 추가 (inote / inote-ai)

> 2026-11-06 계약 합의. 채팅(`inote` LLM)에 "내일 할 일 정리했어, 이거 추가해줘" 같은 글을 보내면 LLM이 판단해 **할 일 추가를 제안**하고, 사용자가 확인 카드에서 승인하면 기존 할 일 API로 추가한다.
> 순서는 이 프로젝트의 규칙대로 **계약 합의 → FE(MSW) → inote-ai → 통합 확인(로컬)**. `inote-server`는 바꾸지 않는다(`POST /todos`를 그대로 쓴다).
> FE는 화면 하나씩 의논하며 진행한다 — 확인 카드 UI는 만들기 전에 먼저 의논한다.

## 배경
- 지금은 채팅 LLM에 할 일을 추가하는 도구가 없어서 목록을 표로 정리만 해준다.
- `inote-ai`의 `chat.py`에는 글 초안용 `start_draft` 도구 패턴이 이미 있다(모델이 도구 호출 → 서버가 SSE 이벤트 전송). 같은 패턴으로 도구 하나를 더 만든다. 별도 에이전트 프레임워크나 Claude Code 스킬은 필요 없다.

## 결정 사항
- **확인 카드**: 바로 추가하지 않고 사용자가 카드에서 승인해야 추가한다. (오판이 DB에 바로 들어가지 않게)
- **모든 채팅에서 켠다**: `can_todo` 같은 플래그 없이 항상 도구를 제공한다. 요청 모양이 안 바뀌어 하위 호환 문제가 없다.
- **애매하면 되묻는다**: "정리해줘"·요약 요청에는 도구를 부르지 않는다. "추가해줘"처럼 의도가 분명하고 항목을 알 수 있을 때만 호출. 애매하면 "이 N개를 할 일에 추가할까요?"처럼 묻는다.
- **FE가 `POST /todos`를 호출한다**: `inote-ai`는 인증이 없고 `user_id`를 신뢰하는 구조라 서버를 직접 부르지 않는다. FE가 로그인 세션으로 호출하면 인증을 그대로 쓴다.
- **마감일은 이번에 다루지 않는다**: 제목만. (오늘 날짜 주입·"내일" 해석이 필요해서 후속)
- **카드에서는 항목 제외(체크 해제)만** 가능하다. 제목 수정은 후속.
- **추가하면 채팅은 유지한 채 할 일 페이지(`/todos`)로 이동한다** (2026-11-06). 채팅 상태는 루트 레이아웃(`ChatWorkspace`)이 들고 있어서 페이지를 이동해도 대화·카드가 남는다. 데스크톱은 옆 패널이라 그대로 보이고, 모바일 시트는 페이지를 가리므로 이동과 함께 닫는 쪽으로 제안(확정 전). 전부 성공했을 때만 이동하고, 일부 실패면 채팅에 머문다. 그래서 "할 일 보기" 링크는 두지 않는다.
- **카드 UI**: 완료·취소 후에는 한 줄 요약으로 접는다. 같은 카드로 다시 추가할 수 없다(중복 추가 방지). 일부 실패는 "N개 중 M개 추가, K개 실패" 문구만 보여주고 재시도 버튼은 후속.
- **새로고침하면 카드는 사라진다**: `inote-ai`는 안내 문장만 assistant 메시지로 저장한다(초안 기능과 같은 방식). 카드 상태 저장은 후속.

## 계약 (2026-11-06 승인)

**요청** `POST /chat/stream` — 변경 없음.

**LLM 도구** `propose_todos`
```json
{ "items": [ { "title": "string" } ] }
```
- 서버에서 trim, 빈 제목 제외, 200자로 자름(`CreateTodoDto.title` 최대 200자), 최대 10개.
- 도구 인자가 깨졌거나 항목이 0개면 이벤트를 보내지 않고 일반 답변으로 끝낸다(`start_draft`의 파싱 실패 처리와 같은 방침).

**새 SSE 이벤트** (기존 `{"text": ...}` 이벤트는 그대로)
```json
data: {"todo_proposal": {"items": [{"title": "디라티오 이력서 작성 후 지원"}]}}
```
- 안내 문장(`text`)에 이어 한 번만 나간다.

**시스템 프롬프트 규칙**
- 할 일 추가를 분명히 요청했고 항목을 알 수 있을 때만 `propose_todos` 호출.
- 개념 질문·정리/요약 요청·항목이 불분명한 경우는 호출하지 않고 되묻는다.
- 제목은 짧은 한 줄로 요약하고 URL은 넣지 않는다.

**FE 확인 카드 (UI는 구현 전 별도 의논)**
- 항목 체크리스트(기본 전부 선택) + [추가] [취소].
- [추가] → 선택 항목을 기존 `useCreateTodo`로 하나씩 `POST /todos` → 카드가 "N개 추가됨"으로 바뀜.

## ⚠️ 배포 순서: FE 먼저, inote-ai 나중
현재 FE의 SSE 파서(`widgets/chat-dock/model/useChatMessages.ts`)는 모든 이벤트를 `{ text }`로 가정해서, 모르는 이벤트가 오면 `m.text + undefined`로 **화면에 "undefined"가 찍힌다.** `inote-ai`를 먼저 배포하면 안 된다.

  - [ ] 항목 6개짜리 배열 인자의 파싱 실패율 확인(`gpt-oss-20b`는 긴 인자에서 약 9% 실패한 적 있음)
  - [ ] 도구 파싱 해석 로직은 `inote-ai` 단위 테스트(사용자가 직접 작성 — BE 규칙 적용 여부는 확인 필요)
- [ ] **3단계 통합 확인**: 로컬에서 FE·`inote-ai`·`inote-server`를 함께 띄워 캡처의 6개 항목 메시지로 확인 — ⚠️ 서버는 개발 DB(`scripts/dev-db.sh start`)로만 띄운다. 운영 DB 금지.

## AI가 기능(할 일/글쓰기/독서)을 구별하는 방식 (2026-11-06 결정)
- **이번에는 도구 호출 + 프롬프트 규칙·예시 + 평가용 예문 세트**로 간다. 파인튜닝은 하지 않는다(호스팅 모델이라 불가, 규모에 과함).
- 임베딩은 의도 분류에 직접 쓰지 않는다. 임베딩은 "비슷한 것 검색"이라 "독서모임 가기를 할 일에 넣어줘" 같은 함정(뜻은 독서와 가깝지만 의도는 할 일)에 약하다.
- 파인튜닝을 하려면 무엇을 준비해야 하는지는 `docs/learning/FINE_TUNING.md`에 정리했다(평가 예문 세트가 먼저, 서빙 방법 확인 필요). 평가에서 목표 정확도에 못 미칠 때 다시 검토한다.
- 독서 상담은 URL 기준으로 이미 별도 채팅(`/reading-chat/stream`)이라 모델이 구별하지 않는다. 일반 채팅의 실제 혼동 후보는 할 일 vs 글쓰기.

## 이번에 하지 않는 것 (후속)

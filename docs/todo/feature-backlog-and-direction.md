# 기록 — 진로 방향은 미정, 우선 기능 작업부터 (2026-10-28)

> 2026-10-28 대화 기록. 사용자는 목표 직무·프로젝트 방향을 **아직 정하지 못했고**, 그래서 "우선 기능 작업들을 다 해보자"고 정했다.
> 이 문서는 (1) 그 판단의 배경, (2) 해볼 기능 작업의 후보와 순서(미확정), (3) 아직 정해야 할 것을 남긴다.
> 규칙: 나중에 하기로 한 일은 `docs/todo/`에 기록한다. 결정이 나면 `docs/adr/`로 옮기거나 항목을 완료로 체크한다.

## 1. 배경 (사용자가 한 말, 사실대로)
- 이 사이드프로젝트는 FE·BE 중심의 CRUD이고, LLM은 Groq로 검색·채팅 정도에만 쓴다고 느낀다.
- AI 엔지니어 경험, 실시간 스트리밍 경험이 없어서 지금 채용시장에서 경쟁력이 없다고 걱정한다.
- 방향(목표 직무, 프로젝트를 어디까지 키울지)을 아직 잡지 못했다 → **우선 기능을 만들어 보며 정한다.**

## 2. 코드·이력으로 확인한 현황 (2026-10-28)
"CRUD뿐"이라는 인상과 달리 아래가 이미 있다. (확인은 코드와 커밋 제목 기준이고, 운영 반영 여부는 확인 필요)

| 주제 | 근거 |
|---|---|
| 실시간 스트리밍(SSE) | 서버 `inote-ai/app/routers/chat.py`의 `_sse`로 조각 전송, FE `apps/web/src/widgets/chat-dock/model/useChatMessages.ts`가 `ReadableStream`으로 받아 이어 붙임. 이벤트 종류(`text`, `draft_start`·`draft_text`·`draft_done`·`draft_failed`) 설계됨 |
| LLM 도구 호출 | `inote-ai`의 `start_draft` 도구(`can_draft=true`일 때만), 판단 정확도 평가 스크립트 `scripts/eval_draft_intent.py`(24개 예문) |
| 검색·임베딩 | KURE 임베딩, 비슷한 글 API, 글 찾기 채팅 (`docs/kure/`) |
| 다중 서비스 운영 | FE·BE·AI 3개 서비스, DB 2개, Render 한도 초과 대응·Supabase·Vercel 이전 (`docs/adr/0003-hosting-migration.md`) |
| 품질 관리 | Vitest·MSW·Playwright, 결정 기록(`docs/adr/`), 개발 일지(`docs/devlog/fe.md`) |

**부족한 것(깊이)**: 스트림 취소·끊김 복구가 없음, 평가 결과를 수치로 정리한 것이 없음, 검색 품질 평가 세트(KURE A7)가 없음, 응답 지연·토큰 비용 측정이 없음.
**정직하게 남길 점**: 구현을 AI와 함께 했다면 면접에서 인정되는 것은 "왜 그렇게 했고 어떤 문제를 겪었는지 설명할 수 있는가"다. 모델 학습·파인튜닝·ML 파이프라인은 이 프로젝트에 없고 지금 방식으로는 채워지지 않는다.

| 순서 | 작업 | 상태·근거 |
|---|---|---|
| A | 작은 정리 | (아래 A 목록) |
| B | **채팅 업데이트 1차** (세션 구조 개편, 글 읽기, 글에 넣기, 이름·삭제) | 결정·API 계약 **승인됨, 구현 미착수** (ADR 0006, 2026-10-23 기준). 순서 `inote-ai` → `inote-server` → FE. 진행 체크리스트의 소스는 `docs/handoff/chat-update/README.md` — 여기에 복사하지 않는다 |

왜 이 순서인가(제안): B는 이미 승인돼 있고 C·D가 B의 세션 구조(채팅↔글 연결)와 도구 호출 구조 위에 얹히기 때문이다. A는 작고 B·C의 전제를 정리한다. E는 B~D와 병행할 수 있다.

### A. 작은 정리
- [ ] **AI 주소 끝의 `/` 방어** — `NEXT_PUBLIC_AI_API_URL` 끝에 `/`가 있으면 `//sessions`로 요청돼 Vercel이 308을 돌려주고, CORS 사전 요청이라 브라우저가 실패한다(2026-10-28 로컬에서 겪음). 주소를 읽는 곳(`useChatMessages`, `useReadingChatMessages` 두 곳뿐 — `api.ts`·`auth-client.ts`는 BE 주소용이라 대상 아님)에서 끝의 `/`를 제거. `shared/lib/ai-url.ts`로 구현, **PR #19 진행 중(머지 전)**
- [x] **세션별 동시 진행(2026-10-29 방향 변경: 스트림 취소 → 동시 진행)** — 구현·로컬 QA 완료(미커밋, 브랜치 `feat/chat-concurrent-streams`, QA: `chat-concurrent-streams-qa.md`). — 답변이 오는 도중 새 대화·다른 세션을 고르면 이전 스트림이 끝날 때까지 새 대화 전송이 잠긴다(PR #10의 알려진 한계). 취소하면 서버가 답변을 끝에 저장하므로(`inote-ai` `chat.py` 232~235줄) 답이 사라질 것으로 추정되어, `messages`·`isSending`을 세션별로 나눠 이전 답변은 계속 진행하고 새 대화도 바로 보내게 한다. FE만 변경(서버·API 변경 없음). 아래 "검토했지만 보류한 것" 참고
- [ ] 스트림 끊김·부분 청크 파싱 테스트 보강 (`useChatMessages`는 지금 테스트가 거의 없음 — ADR 0006의 FE 첫 단계와 겹친다)
- [ ] 개발 일지 `docs/devlog/fe.md`에 채팅 코드블록·로딩·스크롤 변경(PR #10) 기록

### C. "넣어줘" 흐름 (목표)
목표: 채팅에서 "넣어줘" → "글을 새로 작성해드릴까요?" → 새 글 화면으로 자동 이동(채팅은 유지) → 제목·본문이 채워짐.

2026-10-28 조사 결과(ADR 0006 확인 전의 분석이라, B 이후 재확인 필요):
- AI 서버의 `start_draft` 도구와 `draft_*` 이벤트는 구현돼 있으나 FE가 `can_draft`를 보내지 않고 `{text}` 이벤트만 읽는다. 에디터에 값을 넘기는 통로가 없다 (FSD상 채팅 위젯과 글쓰기 기능은 서로 import 불가 → `shared`의 중간 매개체 필요, ADR 0006 2절과 같은 지적)
- `/write/{id}` 진입 시 채팅 세션이 그 글로 강제 전환돼 대화가 초기화되는 문제 → **B의 결정 3·5(채팅은 독립, 글에 자동 연결)로 구조가 바뀐다.** 개편 후 "이동해도 대화 유지"를 다시 설계해야 한다
- `/write`는 이어 쓸 draft가 있으면 선택 모달이 먼저 떠서, 자동 흐름은 FE가 draft를 직접 만들고(`POST /blog/posts/draft`) `/write/{id}`로 바로 이동해야 한다 (`WritePostForm.tsx`)
- 서버의 도구는 글쓰기 화면 전용 설계(`can_draft`)라 다른 화면에서 "넣어줘"를 받으려면 설계 확장이 필요하다

**미결정 질문과 제안(2026-10-28)** — 사용자가 아직 답하지 않았다
1. 확인 질문 방식: (A) LLM이 자연어로 되묻기 (B) **FE 확인 카드 [새 글로 작성] [취소]** ← 제안
2. 초안 생성 시점: (A) 서버가 즉시 쓰고 FE가 버퍼링 (B) **서버가 제안만 보내고 수락 후 본문 생성** ← 제안(`inote-ai` 변경 필요)
3. 대화 유지: 새 글 세션 전환을 건너뛰고 현재 대화 유지. 이후 대화를 새 글에 연결할지는 `inote-ai` 세션 저장 방식 확인 후 (B의 연결 구조와 함께)
4. 에디터 반영: **완료 후 한 번에** vs 실시간 채우기(미완성 마크다운을 Tiptap에 계속 넣어야 해서 어려움)
5. 이미 `/write`에 있을 때 "넣어줘": 항상 새 글 vs 편집 중인 글에 넣기
6. 로그인 사용자에게만 제공할지
- 단계 제안: 1단계(서버 변경 없음) `/write` 화면에서만 `can_draft`를 켜고 `draft_*`를 에디터에 반영 → 2단계 다른 화면에서의 확인 카드·자동 이동·대화 유지

### D. 할 일·독서·글쓰기 자동 구별
- "학습"이 아니라 **도구 설계 + 예문 평가**로 푼다: `create_todo`·`start_reading_log`·`start_draft` 같은 도구를 모델이 고르게 하고(function calling), 예문 평가 세트로 정확도를 잰다. `start_draft`·`eval_draft_intent.py`가 이미 같은 구조다
- 순서: 도구 정의(설명·인자) → 평가 세트(애매한 경우 포함) → 정확도 확인 → 확신이 낮으면 되묻기 → **사용자 확인 후 실행**(글 생성·할 일 추가는 되돌리기 번거롭다)
- 주의: 독서 기록과 글쓰기는 경계가 겹침(책 감상문), 필수 인자(기한·책 제목) 환각 방지, 비공개 글을 외부 LLM(Groq)에 보낼 때의 정책
- 파인튜닝은 예문·도구 설명을 다듬어도 안 될 때만 검토

### E. 측정·평가·기록
- [ ] 도구 선택 정확도, 검색 정확도(recall@k 등)를 표로 남기기 — KURE 평가 세트(A7, `docs/kure/HANDOFF.md`)와 연결
- [ ] 응답 지연·토큰 사용량 로그 — BE 모니터링 계획(`inote-server` ADR 0002)과 연결
- [ ] 과정을 블로그·포트폴리오로 정리 (`docs/blog/`) — "무엇을 재고 무엇이 달라졌나" 중심

### 검토했지만 보류한 것 — 답변 도중 새 대화 시 MQ(큐) 사용 (2026-10-28)
현재 동작(코드로 읽은 것, `useChatMessages.ts`): 답변이 오는 도중 "새 대화"를 누르면 `messages`는 비워지지만 `isSending`·`sendingRef`는 그대로라, 이전 스트림이 끝날 때까지 새 대화 전송이 잠기고 로딩 표시도 없다. 이전 답변 글자는 메시지 id가 없어 버려지지만 서버 연결·생성은 끝까지 간다. 서버(`inote-ai`)가 이 답변을 이전 세션에 끝까지 저장하는지는 **확인하지 않았다**.

"MQ에 넣어뒀다가 완료되면 진행"을 검토한 결론: **지금은 도입하지 않는다.**
- (가) 다음 질문 대기 → 브라우저 안 배열 하나로 충분(서버·MQ 불필요). 같은 대화 안의 "미리 입력"에는 맞고, 새 대화로 옮긴 경우는 보낸 질문이 보류돼 어색하다
- (나) 이전 답변을 백그라운드에서 계속 완성 → 서버 쪽에서 생성과 연결을 분리해야 해서 큐·워커가 필요한데, `inote-ai`가 Vercel(서버리스)이라 계속 떠 있는 워커를 둘 수 없다. 호스팅을 늘려야 하고(`docs/adr/0003-hosting-migration.md`), 답변 한 번이 수 초라 이득에 비해 운영 비용이 크다
- 대안: 세션마다 메시지·전송 상태를 따로 들어 **동시 진행** — 큐 없이 잠금이 풀리지만 상태 구조를 바꾸는 큰 리팩터라 ADR 0006(세션 구조 개편) 때 다시 검토
- 결정(제안): 지금은 AbortController로 중단(A), 필요하면 같은 대화 안 FE 큐 추가. 중단된 답변을 서버가 어떻게 저장하는지는 `inote-ai` 확인 후 정한다
- **서버리스(Vercel) 제약으로 지금 못 하는 것** (2026-10-29): 새로고침·탭 닫기 시 진행 중이던 답변 이어받기(서버가 생성을 연결과 분리해 들고 있어야 함), 백그라운드 생성·재시도 큐. `inote-ai`를 상시 서버로 옮기거나 별도 워커를 둘 때 다시 검토. 세션별 동시 진행(위)을 해도 새로고침하면 진행 중이던 답은 끊기는 한계가 남는다
- MQ는 응답을 기다릴 필요가 없는 진짜 비동기 작업이 생길 때(예: 글 저장 후 임베딩 생성 같은 것 — 현재 처리 방식은 확인하지 않음) 다시 꺼낸다

## 4. 아직 정해야 할 것
1. **목표 직무**: (a) 백엔드·풀스택 개발자(LLM 연동 경험 포함) / (b) 모델·ML 쪽 AI 엔지니어. 우선순위가 달라진다 — (a)라면 A·E와 B·C·D가 맞고, (b)라면 별도 학습 계획이 필요하다
2. **시작 순서**: 위 A→B→C→D(E 병행)를 그대로 갈지
3. C의 질문 1~6 (B 이후에 정해도 된다)
4. ADR 0006의 열린 것은 `docs/handoff/chat-update/README.md` "아직 열려 있는 것"에 있다

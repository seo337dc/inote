## 2차: 메모 여러 장 (1:N) — 계약 확정 2026-11-10
> 1차에서 대상당 unique 제약을 두지 않은 덕에 **서버는 이미 여러 장을 지원**한다(GET은 목록, POST는 매번 새 메모). 1:1처럼 보인 것은 FE가 `list[0]`만 썼기 때문이다. 이번에는 제목·삭제·장 수 상한을 더한다.
> 합의된 결정: **헤더 탭**(한 번에 한 장), **삭제 기능 추가**, **메모마다 제목**, **장 수 상한**, 독서 기록 화면 마운트는 이번 범위 밖(아래 후속).

**`Memo` 모델 변경**: `title String @default("")`(최대 30자) 추가. 마이그레이션은 컬럼 추가뿐이고 기존 메모는 `title: ""`(탭에는 번호 "메모 1…"로 표시). 응답 `Memo = { id, targetType, targetId, title, content, createdAt, updatedAt }`.

> **2026-11-10 변경: 순서 저장 안 함.** 탭 순서 변경은 화면에서만 하고(`←`/`→` 버튼·탭 드래그) 서버에 저장하지 않는다 — 새로고침하면 만든 순서로 돌아온다. 그래서 `position` 컬럼과 `PATCH /memos/reorder`는 **계약에서 뺐다.** 나중에 순서를 저장하고 싶어지면 그때 다시 넣는다.

| 엔드포인트 | 계약 |
|---|---|
| `GET /memos?targetType&targetId` | `createdAt` 오름차순(만든 순서), 본인 메모만 |
| `POST /memos` | 본문 `{ targetType, targetId, title?, content? }`(둘 다 생략 가능). **대상당 최대 10장, 넘으면 409.** 403(남의 대상·작성자 없는 글)·404(대상 없음)는 그대로 |
| `PATCH /memos/:id` | 본문 `{ title?, content? }`(하나 이상, 아니면 400). 404: 없거나 남의 메모 |
| `DELETE /memos/:id` | **신규.** 204. 404: 없거나 남의 메모 |

- 만들기의 "장 수 확인 + 생성"은 한 트랜잭션으로 처리한다(동시에 눌러도 10장을 넘지 않게). 글·독서 기록·회원 삭제 때 메모를 지우는 기존 동작은 그대로다.
- **409는 FE·BE 모두 처리한다**: BE가 막고, FE는 "메모는 최대 10장까지 만들 수 있습니다"를 보여주며 `+` 탭을 비활성화한다.
- 순서: ① 계약(이 절) → ② FE(MSW 목, 화면은 하나씩 의논) → ③ BE(Claude는 테스트 목록·골격만, 사람이 작성) → ④ 통합(로컬 개발 DB에서만). **배포는 BE 먼저**(새 컬럼은 기본값이 있고 새 응답 필드는 기존 FE에 영향이 없다).

- [x] ② FE (2026-11-10): `MemoSaver`를 메모별로 돌리기(메모마다 디바운스·직렬화·재시도), `useMemoDraft`를 메모 목록·현재 탭 기준으로, 헤더 탭 UI(크롬식 탭 줄: 추가·×삭제·더블클릭 이름 변경·드래그/←→ 순서 변경(저장 안 함)·넘친 탭 뱃지+선택 목록·상한 안내)
- [x] ③ BE (2026-11-10, 개발 DB 통합 확인 전): `title` 컬럼과 마이그레이션, `POST` 상한(409)·`PATCH` 확장·`DELETE`, 서비스·DTO 단위 테스트
- [x] ④ 통합 확인(개발 DB, 2026-11-10) — 마이그레이션 적용·드리프트 없음, BE HTTP 24개 시나리오 통과, 실제 FE↔BE 브라우저 확인(첫 입력 POST·`+`·이름 변경·새로고침 복원·삭제·10장 상한)

## 3차: 어느 화면에서나 메모장 + 메모 관리 페이지 — 계약 확정 2026-11-12
> 지금은 메모장이 글쓰기 화면에만 붙어 있다. 어느 화면에서나 쓰게 하고, 내 메모를 모아 보는 관리 페이지를 만든다. 메모 UI 자체의 변경은 나중에 따로 한다(이번 범위 밖).
> 합의된 결정: 메모의 종류는 **일반 / 글 / 독서**. 글쓰기·글 상세에서는 그 글, 독서에서는 그 독서 기록의 메모이고, 홈·목록 등 나머지 화면에서는 **일반 메모**. **남의 글 상세에서는 메모장을 숨긴다**(서버가 남의 글에는 메모를 못 만들게 막는다). 로그인하지 않았으면 숨긴다.

**계약 변경**
| 항목 | 변경 |
|---|---|
| `targetType` | `general` 추가. 일반 메모는 대상이 없어 `targetId`를 받지 않고 서버가 고정값(`""`)으로 저장한다. 대상 소유 확인은 건너뛴다(내 메모면 된다) |
| `POST /memos` | `general`은 `targetId` 없이 만들 수 있다. **일반 메모 전체 10장 상한**(넘으면 409, 글·독서는 기존대로 대상당 10장). 상한 값 조정은 메모 UI를 바꿀 때 다시 본다 |
| `GET /memos` | `targetType`·`targetId`를 모두 생략할 수 있다. 생략하면 내 메모 전체를 **최근 수정순**으로, `targetType`만 주면 종류별로. 기존 호출(둘 다 지정)은 그대로 만든 순서(오름차순) |
| 응답 `Memo` | `targetTitle`(글·독서 제목, 일반 메모나 제목 없으면 `null`) 추가 |

**FE 구조 결정**
- 메모장(`MemoPad`)은 **루트 레이아웃에 하나만** 두고(`widgets/global-memo`의 `GlobalMemoPad`, `ChatWorkspace`의 `floating` 자리 — 본문 컬럼 오른쪽 아래), 현재 경로로 대상을 정한다(`entities/memo`의 `resolveMemoTarget`: `/posts/:id` → 그 글(내 글일 때만), 독서 상세 → 그 독서 기록, 그 외 → 일반). **글쓰기 화면(`/write/:id`)은 지금처럼 상단 바의 자기 메모장을 그대로 쓴다**(AI 패널 폭에 따라 같이 움직이는 현재 동작 유지, 전역 메모장은 거기서 그리지 않음). `/reading/write`는 일반 메모. 관리자(보류)·`/memos`는 숨김.
- 메모 관리 페이지 `/memos`: 진입점은 **헤더 사용자 버튼의 select에 "메모 관리" 항목**. 탭 4개(전체·일반·글·독서), 카드 목록. 카드를 누르면 **대상 글·독서로 이동**하고, 일반 메모는 **메모장을 그 메모 탭으로 열어** 보여준다.

**순서**: ① 계약(이 절) → ② FE(MSW 목, **작업은 하나씩 의논**): 경로 → 대상 결정과 루트 마운트 → 헤더 메뉴 항목 → `/memos` 페이지 → ③ BE(테스트는 사용자가 위임하면 Claude가 작성) → ④ 통합(개발 DB). 배포는 BE 먼저(스키마 변경 없음: `targetType`은 문자열 컬럼, 검증은 DTO).

- [x] ① 계약 확정 (2026-11-12)
- [ ] ② FE
  - [x] 경로 → 메모 대상 결정(`resolveMemoTarget`), 일반 메모 데이터 계층(`MemoTarget`에 `general`, API·캐시 키), 루트 `GlobalMemoPad`(비로그인·남의 글·`/memos`·관리자 숨김, 대상이 바뀌면 새로 마운트) (2026-11-12, 커밋 전 — 실제 BE는 아직 `general`을 모르므로 MSW·브라우저 가짜 응답으로만 확인)

  - [x] `/memos` 관리 페이지 UI — 탭 4개(수 표시)·카드·빈 상태·불러오기 실패, 글·독서 카드는 대상 화면으로 이동. **서버 전체 조회가 없어 `NEXT_PUBLIC_MEMOS_MOCK=true`로 목 데이터(`entities/memo/model/mock.ts`)를 보며 UI 확인**(2026-11-12, 커밋 전)

## 4차: 메모 관리 고도화 — 대상별 묶기·무한 스크롤·메모장 열기 (계약안 2026-11-12, 승인 전)
> 3차의 `/memos`는 메모 한 장이 카드 한 장이라, 같은 글의 메모가 여러 장이면 카드가 반복된다. 대상(글·독서)별로 묶고, 무한 스크롤로 불러오고, 카드의 메모를 누르면 메모장을 크게 연다.
> 합의된 결정: ① 일반 메모는 묶지 않는다(한 장 = 카드 한 장). ② 카드 헤더 = `글|독서` 뱃지 + 대상 제목(길면 …) + `외 N개`(여러 장일 때) + 대상 페이지로 가는 이동 아이콘. ③ 날짜는 지운다. ④ 여러 장이면 날짜 자리에 ‹ › 이동 버튼(과 `1/3`). ⑤ 카드의 메모를 누르면 **편집 가능한 메모장을 크게** 연다(글·독서·일반 모두 그 자리에서). ⑥ 무한 스크롤은 **서버가 대상 단위로 묶어 페이지**를 준다. ⑦ 3차의 `/?memo=ID`(홈에서 열기) 방식과 `useOpenMemoRequest`는 정리한다.

**계약안: `GET /memos/groups` (신규, 로그인 필요)**
| 항목 | 내용 |
|---|---|
| 쿼리 | `targetType`(생략하면 전체, `general`·`post`·`reading`), `cursor`(불투명 문자열, 생략하면 처음), `limit`(기본 20, 최대 50, 그룹 수 기준) |
| 응답 | `{ items: MemoGroup[], nextCursor: string \| null }` — 마지막 페이지면 `nextCursor`는 null |
| `MemoGroup` | `{ key, targetType, targetId, targetTitle: string \| null, updatedAt, memos: Memo[] }` — `memos`는 그 대상의 내 메모 전부(최대 10장), **최근 수정순**. `updatedAt`은 그룹 안 가장 최근 수정 시각 |
| 묶는 규칙 | 글·독서: `(targetType, targetId)` 하나가 한 그룹. 일반: **메모 한 장이 한 그룹**(`key` = 메모 id, `targetTitle` null) |
| 정렬 | 그룹의 `updatedAt` 내림차순, 같으면 `key` 내림차순(키셋 방식 — 새 메모가 생겨도 페이지가 어긋나지 않게) |
| 오류 | 401, 400(`limit` 범위 밖·잘못된 `cursor`·잘못된 `targetType`) |
| 기존 | `GET /memos`(메모장이 대상별로 불러오는 것)는 그대로 |
| 탭 숫자 | **이번에는 내려주지 않는다**(아래 후속) — 탭 숫자는 이번 화면에서 뺀다 |

**FE 구조**: `useMemoGroups(targetType)`(`useInfiniteQuery`) + 스크롤 끝 감지(`IntersectionObserver`)로 다음 페이지. 카드 = 그룹. 카드의 메모를 누르면 `MemoPad`를 **큰 크기·열린 채·대상 지정**으로 띄운다(`target`·`openMemoId`, 닫으면 카드에 반영). 3차의 목 모드(`NEXT_PUBLIC_MEMOS_MOCK`)는 그룹 응답도 흉내 낸다.

**순서**: ① 계약(이 절) → ② FE(MSW 목, 화면은 하나씩) → ③ BE → ④ 통합(개발 DB). 배포는 BE 먼저.

### 4차 후속 (이번에 일부러 미룸)
- [ ] **목 모드의 대량 데이터(`NEXT_PUBLIC_MEMOS_MOCK_EXTRA`)는 일반 메모 10장 제한을 어긴다** — 일반 카드를 열면 메모장이 그 개수만큼 탭을 그려 매우 느려진다(1000개면 사실상 멈춤). 무한 스크롤 확인용 데이터일 뿐이라 일반 메모 카드의 메모장 열기는 `EXTRA`가 작을 때(100 정도)만 확인할 것. 필요하면 목의 `get(general)`을 10장으로 자르는 방안을 검토
- [ ] **가상 스크롤 판단용 측정값 (2026-11-13, 일반 메모 1000개·한 페이지 20개, 목 모드 · 데스크톱 1280×800, 헤드리스 Chromium)**: 운영 빌드 — 1007장까지 약 4.4초(스크롤 간격 60ms 포함)에 이어 붙음, **긴 작업(long task) 0건**, DOM 노드 약 1.2만 개(카드 한 장 약 12개), JS 힙 12→30MB. 개발 서버 — 긴 작업 42건(최대 432ms, 합계 5.8초), 힙 21→89MB. 결론: **1000개까지는 운영 빌드에서 가상 스크롤 없이도 부드럽다**.
  - **5000개 추가 측정(운영 빌드, 일반 메모 5000개)**: DOM 노드 6만 개, JS 힙 약 100MB, 끝까지 이어 붙이기 22초(목 모드·스크롤 간격 포함)·긴 작업 313건(합계 25.7초, 최대 195ms), 스크롤 프레임은 양호(p95 33ms), **카드를 눌러 메모장이 뜨기까지 약 1.0초, 닫기 약 0.8초**, 탭 전환 약 0.15초. 열기·닫기 비용은 스크립트 744ms·스타일 계산 184ms·레이아웃 148ms로 분해된다
  - **보정(같은 날 재측정)**: 위 열기·닫기 1.0/0.8초는 **일반 메모 5000장을 탭으로 한꺼번에 그린 메모장 비용이 섞인 값**이다(실제 서버는 일반 메모를 10장으로 제한하므로 비현실적인 목 데이터). 메모가 3장뿐인 글 카드를 같은 5000개 목록에서 열면 **열기 708ms·닫기 190ms** — 목록 DOM(6만 노드)만의 비용이 열기에 약 0.7초로 실재한다
  - **`React.memo`(+안정 콜백) 실험(원복함)**: 끝까지 이어 붙이는 시간만 22초 → 14초(-36%)로 줄고, 메모장 열기·닫기(1034→965ms, 794→750ms)는 거의 그대로 → **병목은 카드 재렌더가 아니라 거대한 DOM·목록 재조정**이다. DOM 개수를 줄이는 가상 스크롤이 근본 해결
  - 참고: Playwright의 `getByRole` 조회가 6만 노드에서 1초 넘게 걸려 처음 측정값(1.6초)을 부풀렸다 — 페이지 안에서 직접 재야 한다(`performance.now`)
  - **결정(2026-11-13): 목표는 1000개까지 — 가상 스크롤은 지금 적용하지 않는다.** 몇 천 개가 목표가 되면 `@tanstack/react-virtual`로 간다(행 단위 가상화, `main`을 `getScrollElement`로, 카드의 보던 메모 위치를 위로 올려 보존, 카드 수가 적을 때는 가상화 없이 전부 그려 테스트·접근성 유지)
- [x] **메모장을 닫을 때 전체 페이지를 다시 불러오던 문제 해결 (2026-11-13, 커밋 전)** — 닫을 때 고친 대상의 메모만 `GET /memos`로 한 번 받아 받아 둔 그룹 목록(전체·종류별 탭)에 반영한다(`syncMemoGroupsAfterEdit`: 그룹 교체·재정렬·삭제·추가, 아직 받지 않은 더 오래된 그룹은 끼워 넣지 않음, 받기 실패 시 목록 무효화로 대체). 고친 카드가 맨 앞으로 올라오고 목록 스크롤 위치는 유지된다(`overflow-anchor: none`)
- [ ] **가상 스크롤(virtualization) 라이브러리 검토** — 카드를 계속 이어 붙이면 DOM이 늘어난다. `@tanstack/react-virtual` 등을 고려. 메모 수·카드 수 같은 **수치와 최적화(초기 로딩·스크롤 성능)**를 함께 측정해서 정한다(목표 수치 먼저 정하기)
- [ ] **탭 숫자** — 무한 스크롤에서는 전체 개수를 화면이 알 수 없다. 서버가 `counts`(탭별 카드 수)를 내려주는 안과 위 수치 검토를 같이 정한다. 그때까지 탭 숫자는 보이지 않는다

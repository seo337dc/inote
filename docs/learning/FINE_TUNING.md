# 파인튜닝 — 할 수 있는 방법과 준비할 것

> 읽는 시간 약 12분. 목적: "채팅 LLM이 할 일/글쓰기/독서 같은 기능을 더 잘 구별하게 **학습시킬 수 있나**"에 답하기 위해, 파인튜닝이 무엇이고 이 프로젝트에서 어떻게 할 수 있는지, 하려면 무엇을 준비해야 하는지 익힌다.
> 2026-11-06 작성. 서비스별 지원 여부·가격·메모리 수치는 자주 바뀌므로, 쓰기 전에 아래 "출처"를 다시 확인한다. 직접 해본 것이 아니라 **조사한 내용**이다.

## 1. 한 줄로
**이미 만들어진 모델에 우리 예문을 더 학습시켜서, 모델 자체를 우리 용도에 맞게 조금 바꾸는 것**이다. 프롬프트로 "이렇게 판단해"라고 시키는 것과 달리, 시키지 않아도 그렇게 행동하도록 모델 안쪽(가중치)을 고친다.

## 2. 프롬프트·검색·파인튜닝, 뭐가 다른가
| 방법 | 무엇을 바꾸나 | 이 프로젝트의 예 |
|---|---|---|
| 프롬프트·도구 설명 | 모델에게 주는 **지시** | `DRAFT_RULES`, `propose_todos` 설명 (지금 쓰는 방식) |
| 검색(RAG)·동적 few-shot | 모델에게 보여주는 **자료** | 기능 규칙 테이블을 임베딩해 관련 규칙만 프롬프트에 넣기(후속 후보) |
| **파인튜닝** | **모델 자체** | 예문 수백 개로 "할 일 vs 글 초안" 구별을 학습 |

순서는 보통 **프롬프트 → 검색 → 파인튜닝**이다. 오른쪽으로 갈수록 효과가 클 수 있지만 준비·비용·유지 부담이 크게 늘어난다. 규칙이 바뀌면 프롬프트는 문장만 고치면 되지만, 파인튜닝은 **다시 학습**해야 한다.

## 3. 파인튜닝이 잘 맞는 경우 / 안 맞는 경우
- 맞는 경우: 판단 기준이 많고 미묘해서 프롬프트에 다 못 쓸 때, 같은 형식의 출력을 매우 안정적으로 내야 할 때, 작은(싼) 모델로 큰 모델 수준의 정확도를 내고 싶을 때.
- 안 맞는 경우: **새로운 사실을 알려주고 싶을 때**(→ 검색이 맞다. 파인튜닝은 지식 주입에 약하고 틀린 내용을 그럴듯하게 만들 수 있다), 규칙이 자주 바뀔 때, 예문이 몇십 개밖에 없을 때.
- 이 프로젝트는 지금 기능이 2~3개이고 규칙이 열 줄 안팎이라 **프롬프트 + 평가 예문으로 먼저 정확도를 재는 것이 맞다.** 그 결과가 목표에 못 미칠 때 파인튜닝을 검토한다.

## 4. 파인튜닝 종류 (알아둘 용어)
- **전체 파인튜닝(Full FT)**: 모델의 모든 가중치를 학습. GPU 메모리와 비용이 가장 크다. 개인 프로젝트에서는 거의 안 한다.
- **LoRA**: 원래 가중치는 그대로 두고, 작은 "보조 가중치(어댑터)"만 학습. 메모리·시간이 훨씬 적고, 결과물이 작은 파일 하나라 교체하기 쉽다. 사실상 기본 선택지.
- **QLoRA**: 모델을 4비트로 줄여 올린 채 LoRA를 학습. 메모리를 더 줄이는 대신 약간의 품질 손실 가능.
- **SFT(지도 파인튜닝)**: "입력 → 정답 출력" 쌍을 보여주고 따라 하게 학습. 이 프로젝트의 의도 분류·도구 호출 학습은 이 방식이다.
- **선호 학습(DPO 등)**: "A 답이 B 답보다 낫다"는 비교 데이터로 학습. 지금 단계에서는 필요 없다.

## 5. 이 프로젝트에서 할 수 있는 방법 3가지

### 방법 A. 오픈 모델을 직접 LoRA로 학습 (현재 모델 계열)
- 지금 쓰는 `gpt-oss-20b`는 **가중치가 공개된 모델**이라 직접 파인튜닝할 수 있다.
- 학습 도구로는 Unsloth, Hugging Face TRL 같은 것이 쓰인다. 조사한 바로는 QLoRA(4비트)로 약 **14GB(권장 16GB 이상) VRAM**, BF16 LoRA는 약 **44GB**가 필요하다고 한다(Unsloth 문서 기준, 벤더 수치이므로 확인 필요). 무료 Colab GPU로 가능한 범위인지는 직접 확인해야 한다.
- 가장 큰 문제는 **학습 후의 서빙**이다. 지금은 Groq가 모델을 호스팅해 주는데, 우리가 학습한 모델을 올리려면 아래 방법 B를 쓰거나 직접 GPU 서버(vLLM 등)를 운영해야 한다. 무료 티어 구조(Render 무료, Vercel)와 맞지 않고 비용이 생긴다.

### 방법 B. Groq의 LoRA 어댑터 배포 기능
- Groq는 **어댑터를 학습해 주지는 않고, 외부에서 학습한 LoRA 어댑터를 올려서 추론만** 해 준다. 어댑터는 Groq가 지원하는 **정확한 기반 모델 버전**으로 학습해야 한다.
- 이용하려면 Groq에 문의해 접근 권한을 받아야 하고, 가격은 엔터프라이즈 문의로만 안내된다. 출시 당시 지원 모델은 Llama 3.1 8B / 3.3 70B였고 지금은 달라졌을 수 있다(현재 문서 확인 필요).
- 개인 프로젝트에서는 현실적이지 않을 가능성이 크다. 지금 모델(`gpt-oss-20b`)이 지원 목록에 있는지도 확인해야 한다.

### 방법 C. 임베딩 + 작은 분류기 학습 (모델은 그대로)
- 이 프로젝트에서 가장 가벼운 "학습"이다. 예문을 임베딩(KURE)해서 숫자 벡터로 만든 뒤, 그 위에 **작은 분류기**(로지스틱 회귀 등, GPU 불필요)를 학습해 "할 일 / 글쓰기 / 일반 질문"을 가른다.
- 장점: 학습이 몇 초, 서빙 비용 거의 없음, 예문 추가 후 재학습이 쉬움.
- 한계: 임베딩은 **뜻의 유사도**를 담는 것이라 "독서모임 가기를 할 일에 넣어줘"처럼 단어는 독서인데 의도는 할 일인 문장에 약할 수 있다. 또 의도를 가르는 것까지만 하고, 항목을 뽑아 제목으로 요약하는 일은 여전히 LLM의 도구 호출이 한다. 채팅마다 임베딩 호출이 늘고 임베딩 서버(KURE)에 의존하게 된다(`docs/todo/kure-hosting.md`).

## 6. 파인튜닝 전에 준비할 것 (체크리스트)
1. **평가 예문 세트** — 학습보다 먼저. 학습 전/후(그리고 프롬프트 방식과)를 같은 예문으로 비교해야 "좋아졌는지" 안다. `inote-ai/eval/`의 방식을 확장한다. 함정 문장(단어는 독서인데 의도는 할 일)을 반드시 넣는다.
2. **학습 데이터** — "사용자 메시지 → 올바른 판단(도구와 인자)" 쌍. 보통 기능당 **수십~수백 개**가 필요하다. 모으는 방법: 직접 쓰기, 실제 채팅 기록에서 뽑기(개인정보·사생활이므로 본인 데이터만, 비식별 확인), LLM으로 변형해 늘리기(품질 검수 필요).
3. **데이터 분리** — 학습용 / 검증용 / **최종 시험용(절대 학습에 안 씀)** 으로 나눈다. 시험용이 학습에 섞이면 점수가 거짓으로 높게 나온다.
4. **형식 맞추기** — 대화 + 도구 호출을 모델이 기대하는 형식(JSONL)으로 변환. 모델마다 형식이 달라서 학습 도구의 문서를 따른다.
5. **기준선과 목표** — 프롬프트 방식의 현재 정확도(기준선)와, 파인튜닝이 의미 있으려면 얼마나 올라야 하는지(목표) 먼저 정한다. 몇 % 오르려고 서빙 비용·유지 부담을 늘릴 가치가 있는지 판단.
6. **서빙 계획** — 학습한 모델/어댑터를 어디서 돌릴지(비용 포함). 이게 정해지지 않으면 학습해도 쓸 수 없다.
7. **유지 계획** — 기능이 늘거나 규칙이 바뀌면 재학습·재평가가 필요하다는 점을 받아들일 것.

## 7. 학습 순서 제안 (처음이라면)
1. 평가 예문 세트 만들기(어차피 프롬프트 방식에도 필요) → 현재 정확도 측정
2. 정확도가 모자란 유형을 보고 프롬프트·도구 설명 개선, 필요하면 기능 규칙 테이블 + 임베딩 검색(동적 few-shot)
3. 그래도 모자라면 **방법 C**(임베딩 + 분류기)로 가볍게 실험
4. 그다음에도 필요하면 Colab에서 작은 오픈 모델로 **LoRA 실험**(방법 A) — 서비스에 붙이는 것이 아니라 "해보며 배우는" 단계로
5. 서빙 방법과 비용을 확인한 뒤에야 서비스 적용 여부 결정

## 8. 이 프로젝트의 결정 상태
- 2026-11-06: 이번 기능(채팅에서 할 일 추가)은 **도구 호출 + 프롬프트 규칙 + 평가 예문**으로 간다. 파인튜닝은 하지 않는다. (`docs/todo/chat-add-todos.md`)
- 파인튜닝은 위 평가에서 목표 정확도에 못 미칠 때 다시 검토한다.

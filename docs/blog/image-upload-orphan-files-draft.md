## 1. 업로드 API가 되는지 확인하기

**상황**: BE에 `POST /uploads/image`(로그인 필요, 5MB 이하, jpeg/png/webp/gif만)가 이미 있었고 R2에 저장한 뒤 공개 URL을 돌려준다. FE에서는 글 썸네일과 독서 표지에서 쓴다.

**확인 방법 두 단계**
1. **저장소만 따로 확인** — 로그인이 필요한 API라 바로 호출할 수 없어서, 실제 업로드를 맡은 `R2Service`를 `.env` 값으로 직접 호출했다. 1x1 PNG를 올리고 → 공개 URL이 같은 내용으로 열리는지 보고 → 테스트 파일을 지웠다(삭제 후 404 확인).
2. **컨트롤러 검증 확인** — R2는 가짜로 바꾸고 인증 가드는 테스트에서만 우회해서 케이스별로 응답을 봤다.

| 케이스 | 결과 |
|---|---|
| png, webp(확장자 대문자) | 201 |
| pdf, svg | 400 |
| 5MB 초과 | 400 |
| 파일 없음 / 필드명 틀림 | 400 |
| 내용은 텍스트인데 `image/png`로 위장 | 400 (파일 앞부분을 읽어 판별) |

3. 마지막으로 로컬에서 **로그인한 상태로 실제 업로드**를 했고, R2에 올라간 것까지 확인했다.

**배운 점**: "로그인 때문에 못 테스트한다"에서 멈추지 말고, 인증이 걸린 층과 저장소 층을 나눠서 확인할 수 있다.

## 2. 함정 ① 정상 PNG가 400으로 거절된다 (Jest)

컨트롤러 검증 테스트를 돌렸더니 **정상 PNG와 WEBP도 400**이었다. 메시지는 `current file type is image/png, expected type is /^image\/(jpeg|png|webp|gif)$/` — 형식이 맞는데 거절한다.

- **원인**: Nest 11의 `FileTypeValidator`는 mimetype 문자열이 아니라 **파일 앞부분(매직 넘버)을 읽어서** 형식을 판별한다. 이때 쓰는 `file-type` 패키지가 ESM인데, **Jest에서는 실험 플래그가 없으면 이 ESM을 불러오지 못해서** 항상 거절한다. 소스에도 이 경고 문구가 있었다.
- **해결**: `NODE_OPTIONS=--experimental-vm-modules`를 켜고 돌리면 정상 통과했다.
- **부수 효과(좋은 점)**: 매직 넘버로 판별하므로 확장자·Content-Type만 위조한 파일을 걸러낸다.
- **기억할 점**: 이 컨트롤러의 단위 테스트를 쓸 때는 같은 플래그가 필요하다. 코드 버그가 아니라 **테스트 환경의 한계**였다.

## 3. 함정 ② 로컬 BE만 500 — `EMAXCONNSESSION`

로컬에서 FE와 BE를 띄우자 글 목록이 500이었다. FE 콘솔은 `ApiError: Internal server error`(연결 실패가 아니라 BE가 500을 돌려준 것).

BE 로그의 핵심:
```
FATAL: (EMAXCONNSESSION) max clients reached in session mode - max clients are limited to pool_size: 15
```
Supabase Session pooler(5432)는 동시 연결을 **15개**까지만 허용하는데 이미 찬 상태였다.

**진단 과정**
1. 처음 의심: "내 로컬 Prisma가 너무 많이 연다" (Prisma 기본 풀은 `CPU 코어 × 2 + 1`, 8코어면 17).
2. 확인: 로컬 BE가 실제로 잡은 연결은 **1개뿐**이었다 → 로컬이 범인이 아니다.
3. Supabase SQL Editor로 `pg_stat_activity`를 집계: `Supavisor` 연결 **16개가 전부 idle**. 일을 하지 않는 연결을 한도만큼 쥐고 있는 전형적인 **연결 풀** 모습이다.
4. 운영 BE는 이미 자기 연결을 쥐고 있어서 정상 동작하고, 새로 붙으려는 로컬만 자리가 없는 상황과 맞아떨어진다.

**시도한 해결**
| 시도 | 결과 |
|---|---|
| 로컬 `DATABASE_URL`에 `connection_limit=3` | 실패 — 로컬은 원래 1개만 쓰고 있어서 한도를 줄여도 남의 자리는 안 생김 |
| 포트를 **6543(Transaction pooler)** 으로 변경 + `pgbouncer=true&connection_limit=3` | **성공** — 목록이 200 |

**솔직한 한계(글에 꼭 적을 것)**
- 누가 15개를 쥐고 있는지는 **끝내 확인하지 못했다**. "운영 BE 하나가 혼자 채웠을 것"은 정황에서 나온 **추정**이다(Supavisor 연결은 전부 `Supavisor`로 보여서 구분이 안 됨).
- 6543이 통한 이유(모드별로 풀이 따로 있다)도 이 프로젝트에서 직접 검증한 것이 아니라 동작을 보고 판단한 것이다.
- 이게 사실이라면 **운영도 위험**하다(다른 클라이언트가 하나만 더 붙어도, 배포 중 인스턴스가 겹쳐도 실패할 수 있음). 운영 쪽 `connection_limit` 설정은 후속 과제로 남겼다.
- 목록 API 한 번에 쿼리가 4개(고정 글·일반 글 각각 `findMany`+`count`) 동시에 나간다. **쿼리 수 자체가 문제는 아니고**, 풀 크기에 상한이 없는 설정이 근본이다. (다만 요청 하나가 연결을 4개 쓰니 풀이 빨리 찬다.)

**배운 점**: 에러 메시지를 읽고 "내가 범인인가?"부터 **숫자로** 확인했다(내 연결 수 → 전체 연결 수). 추측으로 설정부터 바꾸면 헛수고가 된다(`connection_limit=3`이 그 예).

## 4. 본론 — 업로드하면 R2에 계속 쌓인다

업로드 API는 **DB 기록 없이 R2에 바로 저장**하고 URL만 돌려준다. 그래서 다음 경우마다 파일이 남는다.

| # | 고아 파일이 생기는 경우 |
|---|---|
| 1 | 올리고 저장하지 않고 나감 |
| 2 | 저장 후 다른 이미지로 교체 |
| 3 | 저장 후 이미지 제거 |
| 4 | 기록 삭제 (DB 행만 지워짐) |
| 5 | 회원 탈퇴 — DB의 `onDelete: Cascade`로 지워져서 **앱 코드를 거치지 않는다** |

추가로, `R2Service`에는 삭제 기능 자체가 없었고, URL이 공개 주소라서 **비공개 글을 지워도 이미지는 URL을 아는 사람에게 계속 열린다**.

## 5. 전략 비교와 최종 결정

**후보**
- A. 업로드 기록 테이블 + 정리: 정확하지만 마이그레이션과 상태 관리가 많다
- B. **참조 기반 청소(스윕)**: R2 파일 목록과 DB의 참조를 비교해 안 쓰는 파일 삭제 — 모든 경우를 한 번에 처리
- C. 임시 폴더 + R2 수명주기 규칙(자동 만료): 코드는 필요 없지만 **파일 나이만** 본다
- D. 저장할 때 올리기(브라우저에 들고 있다가): 1번만 해결
- E. 방치

**최종 결정 (대화로 정한 것)**
1. **범위**: 우선 **독서 표지에만** 적용한다. 글 썸네일은 기존 동작 유지(다음 단계에서 같은 구조로 확장).
2. **폴더**: 임시는 `tmp/reading/<userId>/…`, 발행하면 `reading/<userId>/…`로 승격(복사 후 삭제 — S3 호환 API에는 "이동"이 없다).
3. **배치 규칙은 하나로 통일**:
   > R2 파일 중, **DB 어디에서도 참조하지 않고**, 마지막 수정 후 **24시간**이 지난 것을 삭제한다 (`tmp/`·`reading/` 모두)
   - 이 규칙 하나로 위 1~5번이 모두 정리된다. 24시간 유예는 저장 전 새 업로드를 보호한다.
4. **표지 URL은 우리 R2 주소만 허용**(본인 폴더인지도 검사). 지금은 문자열이면 뭐든 저장된다. FE는 업로드 결과로만 값을 채우므로 흐름은 안 깨진다.
5. **draft는 내용과 함께 삭제**: 임시저장된 글·독서 같은 콘텐츠를 이미지와 함께 배치가 정리한다. 순서는 ① 오래된 draft 삭제 → ② 참조가 사라진 이미지 삭제. 보관 기간은 **아직 미정**(기준은 생성일이 아니라 마지막 수정일).
6. **배치 실행**: 외부 호출(cron-job.org)에 의존하지 않는다. 작업 본체를 HTTP와 무관한 서비스로 만들고 **앱 안의 `@Cron`(시간대 `Asia/Seoul`, 새벽 3시)** 과 **독립 실행 스크립트** 두 방식으로 붙인다.

**왜 "나이"가 아니라 "참조"인가 (이 글의 핵심 포인트)**
처음엔 "tmp에서 24시간 지난 파일 삭제"만 생각했다. 그러나 독서는 **임시저장(자동저장)** 이 있어서 draft가 tmp 이미지를 **참조한 채 오래 살 수 있다.** 파일 나이만 보면 살아 있는 draft의 이미지가 깨진다. 그래서 규칙이 "참조 여부 + 유예 시간"이 되었다. R2 수명주기 규칙은 나이만 볼 수 있어서, 쓴다면 아주 넉넉한 안전망 용도다.

## 6. 놓치기 쉬운 점 (체크리스트처럼 쓰기 좋음)
- **자동저장과 승격 시점**: 자동저장 때마다 옮기지 말고 **발행 때** 옮기는 것이 단순하다. 대신 배치가 참조를 확인해야 한다.
- **저장된 파일은 FE가 직접 지우지 못하게**: 클릭 순간에 지우면 수정하다 취소했을 때 DB는 옛 파일을 가리키는데 파일이 없다. 저장이 성공한 뒤 서버가 지운다.
- **소유 검증**: 키에 `userId`를 넣고, 요청자와 같은지 확인하지 않으면 남의 tmp 파일을 자기 기록에 가져올 수 있다.
- **"표지 없음"은 빈 문자열**: 삭제 버튼이 `""`를 보내고 BE가 그대로 저장한다. `null`과 둘 다 "참조 없음"으로 다뤄야 한다.
- **확장자는 사용자 파일명이 아니라 검증된 타입에서**: 지금은 파일명에서 가져와서 `noext`나 `.html` 같은 키가 생길 수 있다(실제로 확인함).
- **시간대**: 서버가 UTC면 새벽 3시(KST)는 전날 18:00 UTC다. 스케줄에 시간대를 명시한다.
- **Render 무료는 유휴 시 잠든다**: 앱 안의 스케줄러는 서버가 깨어 있어야 돈다. 지금은 외부 핑이 깨워 두고 있어서 **간접 의존**이 남는다(항상 켜진 호스팅으로 옮기면 사라짐).
- **`r2.dev` 공개 주소**: 알려진 바로는 개발용이라 운영에는 커스텀 도메인이 권장된다(공식 문서로 확인 필요). 도메인을 바꿀 수 있으니 **DB에는 URL 전체가 아니라 경로(키)만 저장**하는 안을 검토 중이다.
- 이 배치는 사용자의 **작성 중인 내용(draft)을 영구 삭제**한다. 보관 기간을 넉넉히 잡고 삭제 건수를 로그로 남긴다.

## 8. (별도 글 후보) 미해결 이슈 — 글 저장 시 403
이 글과는 별개로, 가이드 문서를 에디터에 붙여 넣어 저장하면 `PATCH /blog/posts/:id`가 403을 돌려줬다. **원인은 아직 확정되지 않았다.**
- 코드상 Nest의 403은 "작성자 불일치" 한 곳뿐이고, 로그인 문제는 401이다.
- 응답 헤더에 Cloudflare 흔적이 있고 Nest가 안 붙이는 `Cache-Control` 조합이 보여서 **엣지(WAF)가 본문의 셸 명령·SQL 문자열을 오탐했을 가능성**을 의심 중이다(추정).
- 확인 순서와 가설은 [`0005-save-403-investigation.md`](../adr/0005-save-403-investigation.md)에 있다. 결론이 나오면 후속 글로 쓰는 것이 좋다.

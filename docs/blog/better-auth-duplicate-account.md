# (제목 초안) 어느 날 구글 로그인만 안 됐다 — better-auth 버전이 올라가며 드러난 중복 계정

> 작성 방식: 아래는 **사실 정리 초안**이다. 문장·톤·강조는 본인 글에 맞게 다듬고, 각 `확인 필요`는 직접 확인한 뒤 지운다.
> 로그·SQL 결과에 실제 이메일·사용자 id·계정 id를 쓸 때는 **가려서** 올린다. 아래 초안에는 넣지 않았다.

---

## 1. 증상

- 로컬에서 `inote`(Next.js)를 띄우고 **구글 계정으로 로그인**하면 구글 계정 선택 직후 실패했다.
- 화면에는 **"문제가 발생했습니다. 잠시 후 다시 시도해주세요."** 토스트만 떴다.
- **이메일/비밀번호로 만든 테스트 계정은 로그인이 됐다.** 구글 로그인만 안 됐다.
- 브라우저 네트워크 탭에는 아무것도 남지 않았다. 구글로 갔다가 돌아오는 리다이렉트 중에 페이지가 새로 로드되면 기록이 지워지기 때문이다. (Preserve log를 켜면 요청은 남지만, 이번에는 서버 로그가 훨씬 빨랐다.)

## 2. 단서를 모은 순서

1. **토스트 문구 해석** — FE는 better-auth가 돌려주는 에러 코드를 한글 문구로 바꿔 보여준다. 코드를 알고 있으면 전용 문구(`state_not_found`, `account_not_linked` 등)가 뜨고, **모르는 코드면 기본 문구**가 뜬다. 즉 "FE가 모르는 종류의 실패"라는 것까지만 알 수 있었다. (코드는 FE가 읽은 뒤 주소에서 지워서 화면에는 남지 않는다.)
2. **서버 로그 확인** — 실패한 순간의 BE 로그에 아래 두 줄이 있었다.
   ```
   ERROR [Better Auth]: Better auth was unable to query your database.
   Error: [BetterAuthError: Multiple accounts match the same accountId for provider "google".
          Resolve duplicate account identities before continuing.]
   ```
   첫 줄만 보면 "DB 연결 문제"로 오해하기 쉽다. **원인은 바로 뒤 `Error:`에 있었다** — 같은 구글 계정이 여러 번 저장돼 있다는 뜻.
3. **그렇다면 왜 이메일 로그인은 되는가** — 이메일/비밀번호 로그인은 `account`를 구글 방식(`providerId` + `accountId`)으로 찾지 않아서 이 검사를 거치지 않는다. 구글 로그인만 이 조회를 하므로 증상과 맞았다.
4. **DB 확인** — 중복이 정말 있는지 조회했다.
   ```sql
   select "accountId", count(*)
   from account
   where "providerId" = 'google'
   group by "accountId"
   having count(*) > 1;
   ```
   한 사용자의 구글 계정이 `account`에 **2행**으로 들어 있었다. 둘 다 같은 사용자에 연결돼 있었고, 다른 사용자에게는 중복이 없었다. 두 행의 차이는 `issuer` 컬럼과 생성일뿐이었다.

   | 행 | `issuer` | 생성 시기 |
   |---|---|---|
   | 옛 행 | `local:oauth:google` | 6월 (구글 로그인을 처음 붙였을 때) |
   | 새 행 | `https://accounts.google.com` | 9월 11일 |

## 3. 왜 중복이 생겼나

better-auth가 `account` 행을 **어떤 키로 찾는지**가 버전마다 달랐다.

| 버전 | 구글 계정을 찾는 기준 | 중복 행이 있으면 |
|---|---|---|
| **1.7.2** | `issuer` + `accountId` | 조용히 새 행을 하나 더 만들었다 |
| **1.7.3 이상** | `providerId` + `accountId` (`issuer` 사용 안 함) | `Multiple accounts match…` **에러** |

(1.7.2와 1.7.14 소스를 직접 내려받아 비교해 확인했다. 중복 검사 문구는 1.7.3부터 들어 있다.)

**흐름을 짜 맞추면:**
1. 6월: 구글 로그인을 붙임. `account` 행이 `issuer = local:oauth:google`로 저장됨.
2. 9월: better-auth 1.7.x가 구글이 알려주는 정식 issuer(`https://accounts.google.com`)를 쓰기 시작. 로그인하자 **기존 행의 `issuer`와 달라서 못 찾고**, 같은 사용자에게 **새 행을 하나 더 만들었다.** 이 버전은 `issuer`로만 찾아서 새 행만 보이니 증상이 없었다.
3. 10월: 배포 환경의 better-auth가 **1.7.3 이상**으로 올라갔다. 이 버전은 `providerId`+`accountId`로 찾고, **2개 이상이면 에러**를 낸다 → 숨어 있던 중복이 처음으로 드러났다.

핵심은 **"코드는 안 바꿨는데 의존성이 바뀌어서 오래된 데이터의 문제가 드러난 것"** 이라는 점이다.

## 4. 왜 배포 환경의 버전이 바뀌었나

- `package.json`에 `"better-auth": "^1.6.16"`처럼 **범위(`^`)** 로 적혀 있었다.
- 로컬에는 lockfile(`pnpm-lock.yaml`)이 **1.7.2**로 고정돼 있었는데도, 배포 서버의 로그에는 그보다 새 버전에만 있는 에러 문구가 찍혔다. 즉 **배포 빌드가 lockfile을 그대로 따르지 않았다.** (Render 빌드 명령이 `pnpm install --prod=false`였고, `--frozen-lockfile`은 없었다.)
- 확인 필요: Render 빌드 로그에서 실제 설치된 better-auth 버전. (코드로 추정한 값은 1.7.12 — 10월 21일 배포 시점의 최신 버전.)

## 5. 해결

**데이터 (운영 DB)** — 중복 중 **옛 `issuer`(`local:oauth:google`) 행**만 삭제했다.
- 두 행이 같은 사용자 소유라 사용자·글에는 영향이 없다.
- 삭제 전에 지울 행이 **정확히 1개**인지 조회로 먼저 확인하고, 같은 조건으로 `delete`를 했다. 운영 DB 변경은 되돌릴 수 없으니 "먼저 SELECT로 보고, 같은 WHERE로 DELETE" 순서를 지켰다.
- 이후 구글 로그인이 정상 동작했다.

**코드 — 같은 일이 다시 생기지 않게**
- `better-auth`를 **정확한 버전(`1.7.12`)으로 고정**하고 lockfile을 맞췄다. `^`를 없애서 설치 때마다 버전이 움직이지 않게 했다.
- Render 빌드 명령에 **`--frozen-lockfile`** 을 넣어, lockfile과 `package.json`이 어긋나면 빌드가 **실패**하게 했다(조용히 새 버전을 설치하지 않게).

**버전 선택에서 부딪힌 것** — 최신(1.7.14)으로 올리려 하자 pnpm이 "릴리스된 지 하루도 안 된 패키지"라며 `minimumReleaseAgeExclude`로 예외 처리를 요구했다. 공급망 공격 대비용 지연(`minimumReleaseAge`)이라, 이 보호를 우회하지 않고 **릴리스 후 며칠 지난 1.7.12**로 정했다.

## 6. 배운 점

1. **로그의 첫 줄만 믿지 않는다.** "unable to query your database"는 DB 장애처럼 보이지만 진짜 원인은 바로 뒤 줄이었다.
2. **"어제까지 됐는데 오늘 안 된다"는 코드가 아니라 의존성·데이터를 의심한다.** 코드 변경 이력이 없다는 것을 확인하는 것이 방향을 잡는 데 도움이 됐다.
3. **범위 의존성(`^`)은 배포 환경마다 다른 버전을 만들 수 있다.** 인증처럼 데이터 형식과 맞물린 라이브러리는 버전을 고정하고, lockfile을 지키도록 빌드를 강제한다.
4. **라이브러리가 쓰는 DB 컬럼의 의미는 버전마다 바뀔 수 있다.** 여기서는 `account.issuer`가 그랬다. 업그레이드 가이드(변경 이력)를 읽고, 기존 데이터가 새 규칙에서 어떻게 해석되는지 확인해야 한다.
5. **운영 데이터를 고칠 때의 절차** — 조회로 대상 확인 → 같은 조건으로 변경 → 결과 행 수 확인. 직접 실행하지 못하는 환경(운영 DB)에서는 SQL을 정리해 사람이 실행하게 한다.

## 7. 확인이 더 필요한 것 (글에 쓰기 전에)
- [ ] Render 빌드 로그에서 실제 설치된 better-auth 버전
- [ ] 중복이 만들어진 정확한 로그인 시점과 당시 서버 버전 (9월 11일 행이 1.7.2에서 만들어졌다는 것은 추정)
- [ ] 이 글에서 인용한 better-auth 변경 내용을 공식 릴리스 노트(또는 업그레이드 가이드)에서 한 번 더 확인
- [ ] 나머지 사용자의 `account` 행은 `issuer`가 `local:oauth:google` 하나뿐이어도, `providerId`+`accountId`로 찾는 현재 버전에서는 문제가 없는지 (직접 한 번 로그인해 확인)

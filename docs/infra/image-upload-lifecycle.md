# 이미지 업로드 정리 전략 — 논의 기록 (2026-10-13, **방향 확정 · 미구현**)

> 사용자와 의논한 설계의 기록이다. **방향은 10절에서 확정**했고 아직 코드는 바꾸지 않았다. 10절의 "아직 미정"이 풀리기 전에는 해당 부분을 구현하지 않는다.
> 관련 코드: `inote-server/src/uploads/`, `inote-server/src/reading-logs/`, FE `WriteReadingLogForm.tsx`

## 1. 문제
`POST /uploads/image`는 **DB 기록 없이 R2에 바로 저장**하고 URL만 돌려준다(키 `uploads/<userId>/<uuid>.<ext>`). `R2Service`에는 `upload`만 있고 삭제가 없다. 그래서 아래 경우마다 이미지가 R2에 남는다.

| # | 고아가 생기는 경우 |
|---|---|
| 1 | 올리고 저장하지 않고 나감 |
| 2 | 저장 후 다른 이미지로 교체 |
| 3 | 저장 후 이미지 제거 |
| 4 | 독서 기록 삭제 (`remove`는 DB 행만 지움) |
| 5 | 회원 탈퇴·관리자 삭제 (`user` → `ReadingLog`가 DB `onDelete: Cascade`라 앱 코드를 거치지 않음) |
| 6 | (예정) 본문 이미지를 올렸다가 지움 — 이번 범위 밖 |

## 2. 확인한 사실 (코드)
- `ReadingLog.coverImageUrl`은 **전체 URL 문자열**이고, DTO 검증이 `@IsString()`뿐이라 **아무 문자열이나** 들어간다(우리 R2 주소가 아니어도 됨).
- 독서 기록은 `publishedAt`이 있으면 **전체 공개**(`findAll`에 작성자·공개 여부 조건이 없음). 미발행(draft)만 본인 전용이다.
- 독서 작성은 draft **자동저장**이 있다(`PATCH`가 `publish` 없이 반복 호출) — 자동저장 때도 `coverImageUrl`이 저장될 수 있다.
- `inote-server`에는 스케줄러(`@nestjs/schedule`)가 없다.
- 현재 공개 URL은 `r2.dev` 주소다. (제가 알기로 `r2.dev`는 개발용이라 운영에는 커스텀 도메인이 권장된다 — 공식 문서로 확인 필요)
- 글 썸네일(`PublishScreen`)도 같은 `POST /uploads/image`를 쓴다 → 독서만 바꿀 때 기존 동작이 깨지면 안 된다.

## 3. 사용자 제안 (2026-10-13)
1. 이미지 업로드는 우선 **독서에만** 적용한다.
2. URL 공개 이슈는 **AWS CloudFront처럼** 적용할 수 있으면 적용한다.
3. **`tmp` 폴더**를 만들어 임시 업로드는 모두 tmp로 보낸다.
4. 독서이므로 **`reading` 폴더**를 만들고, `tmp/reading`도 포함한다.
5. inote-server에 **배치**를 만들어 **매일 새벽 3시**에 돌면서 이미지를 삭제한다.

## 4. 검토 의견

### 4-1. 독서에만 적용 — 동의
범위가 작아져 좋다. 조건: 종류를 지정하지 않은 기존 호출(글 썸네일)은 **지금과 똑같이** 동작해야 한다(`uploads/` 경로 유지). 글은 다음 단계에서 같은 구조(`post/`, `tmp/post/`)로 확장한다. 이미 올라간 `uploads/...` 파일(글 썸네일, 오늘 시험 업로드)은 이번 정리 대상 밖이다 — 수동 정리.

### 4-2. CloudFront식 URL — 독서에는 "서명 URL"이 필요 없고 "CDN/커스텀 도메인"이 해당
- CloudFront에는 두 역할이 섞여 있다: (a) **CDN 캐시와 도메인**, (b) **서명 URL로 접근 제어**.
- 독서 기록은 발행하면 전체 공개라서 표지는 어차피 공개 정보다 → (b)는 불필요하다. 필요한 건 (a): R2 버킷에 **커스텀 도메인을 연결**해 Cloudflare CDN 캐시를 타게 하고 `r2.dev` 주소를 쓰지 않는 것.
- 커스텀 도메인에는 **Cloudflare에 등록된 도메인**이 필요하다 — 보유 여부 미확인.
- (b) 서명 URL은 **비공개 이미지**(예: 비공개 글 본문 이미지)에서 의미가 생긴다 → 글 단계에서 다시 검토. 제가 알기로 R2의 S3 서명 URL은 커스텀 도메인이 아니라 S3 엔드포인트(`*.r2.cloudflarestorage.com`)에서만 동작한다(확인 필요).
- 도메인을 바꿀 가능성을 생각하면 **DB에는 URL이 아니라 키를 저장**하는 편이 낫다(현재는 전체 URL 저장). 바꾸려면 기존 데이터 이전이 필요하다 → 미결정 Q7.

### 4-3. tmp 폴더 — 동의, 단 "승격 시점"을 정해야 한다
흐름(제안):
```
업로드      → tmp/reading/<userId>/<uuid>.<ext>        (임시)
저장(PATCH) → reading/<userId>/<uuid>.<ext> 로 승격     (영구, 이름은 그대로 경로만 변경)
```
- **임시저장(자동저장) 때도 승격해야 한다.** 그렇지 않으면 draft에 tmp URL이 저장된 채로 새벽 배치가 그 파일을 지워서 **draft가 깨진 이미지**가 된다. 승격이 "모든 저장"에서 일어나면 tmp에 남은 파일은 곧 "저장된 적 없는 업로드"라서 DB와 대조하지 않고도 지울 수 있다.
- S3 호환 API에는 "이동"이 없어서 **복사(`CopyObject`) → 삭제(`DeleteObject`)** 두 단계다. 순서: ① 복사 ② DB 갱신 ③ tmp 삭제(최선, 실패해도 배치가 회수).
- **소유 검증 필수**: tmp 키에 `userId`가 들어 있으니, 승격 요청 시 키의 `userId`가 요청자와 같은지 확인해야 한다. 안 하면 남의 tmp 파일을 자기 기록에 가져올 수 있다.
- **`coverImageUrl` 검증이 지금은 없다.** 앞으로는 우리 R2 주소의 `tmp/reading/<본인>/` 또는 `reading/<본인>/`만 허용해야 한다. 단, 카카오 도서 검색 결과의 표지 URL(외부 주소)을 쓰는 흐름이 있는지 확인이 필요하다 → 미결정 Q2.
- 파일 확장자는 사용자가 정한 파일명이 아니라 **검증된 파일 타입**에서 정한다(앞선 점검에서 발견한 개선점).

### 4-4. reading 폴더 — 동의
`tmp/reading/<userId>/…` → `reading/<userId>/…`. 접두어로 정리 범위가 좁혀진다. 업로드 API에 종류 값(`kind=reading`)을 **허용 목록**으로 받는다.

### 4-5. 새벽 3시 배치 — 방향 동의, 주의점이 있다
- **시간대**: 서버가 UTC이면 새벽 3시(KST)는 **18:00 UTC(전날)**이다. 스케줄에 시간대를 명시해야 한다.
- **Render 무료는 유휴 시 잠든다**: 앱 안의 스케줄러(`@nestjs/schedule`, 현재 미설치)는 서버가 **깨어 있어야** 돈다. 지금은 cron-job.org가 10분마다 핑을 보내 깨어 있을 가능성이 높지만 보장은 아니다. 대안은 **내부 시크릿으로 보호된 엔드포인트**를 cron-job.org가 새벽 3시에 호출하는 방식(서버를 깨우는 효과도 있음, 이미 쓰는 도구). → 미결정 Q4.
- **지우는 대상**: `tmp/reading/` 아래에서 마지막 수정이 **24시간(또는 48시간)** 지난 파일. 승격이 모든 저장에서 일어난다는 전제가 있어야 DB 대조 없이 안전하다.
- 한 번에 지우는 개수에 상한을 두고(예: 1,000개), 결과(삭제 개수·실패)를 로그에 남기며, 실패하면 다음 날 다시 한다. 삭제는 반복 실행해도 안전(멱등)해서 배포 중 인스턴스가 둘이어도 문제없다.
- **R2 수명주기 규칙**으로 `tmp/` 접두어를 자동 만료시킬 수 있다면 코드 없이 같은 효과를 낼 수 있다(제가 알기로 R2는 지원하며 단위는 일 — 공식 문서로 확인 필요). 배치의 이중 안전망이나 대체가 될 수 있다.

## 5. 이 제안만으로 정리되는 것과 안 되는 것

| 경우 | 제안(tmp + 새벽 배치)으로 정리되나 |
|---|---|
| 1 저장 안 하고 나감 | ✅ |
| 2 저장 후 교체 | ❌ (옛 파일이 `reading/`에 남음) |
| 3 저장 후 제거 | ❌ |
| 4 독서 기록 삭제 | ❌ |
| 5 회원 탈퇴 cascade | ❌ (앱 코드를 안 거침) |

→ 2~4는 **이벤트 때 삭제**(교체·제거·삭제 시 이전 키 삭제, 최선·실패 허용)로, 5는 **주기적 대조**(예: 주 1회 `reading/` 파일 목록과 DB의 `coverImageUrl` 비교 후, 24시간 이상 참조 없는 파일 삭제)로 보완하는 것을 제안한다. → 미결정 Q6.

## 6. 설계 초안 (승인 전)
- 키: `tmp/reading/<userId>/<uuid>.<ext>` → `reading/<userId>/<uuid>.<ext>`
- 업로드 API: `kind` 허용 목록(`reading`), 없으면 기존 동작 유지
- 독서 `PATCH`(자동저장 포함): `coverImageUrl`이 `tmp/reading/<본인>/`이면 승격 후 DB에는 최종 값 저장, 그 외에는 허용된 접두어만 통과
- 이벤트 삭제: 교체·제거·`remove` 시 이전 키 삭제(최선)
- 배치: 새벽 3시(KST), `tmp/reading/`의 24시간 경과 파일 삭제(+ 주간 대조는 선택)
- 진행 순서(규칙): API 계약 합의 → FE(MSW·유닛 테스트) → BE(테스트 목록·골격은 Claude, 케이스 작성은 사용자) → 통합

## 9. 추가 논의 (2026-10-13, 같은 날)

### 9-1. 배치는 cron-job.org에 의존하지 않게 (사용자 결정)
- 이유: cron-job.org를 나중에 쓰지 않게 될 수 있고, BE 개발자로서 **실제 배치 방식**을 해 보고 싶다.
- 부딪히는 점: Render 무료는 유휴 시 잠든다. 앱 안의 스케줄러는 서버가 깨어 있어야 돌고, 지금 서버를 깨워 두는 것이 cron-job.org 핑이다 → **현재 호스팅에서는 간접 의존**이 남는다. 항상 켜진 호스팅으로 옮기면 사라진다.
- 구조(제안): **작업 본체**를 HTTP와 무관한 서비스 하나(`run()`)로 만들고, 실행 방법을 둘 붙인다.
  1. 앱 안의 `@Cron`(`@nestjs/schedule`, 시간대 `Asia/Seoul`) — Spring `@Scheduled`와 같은 개념
  2. 독립 실행 스크립트(웹 서버 없이 Nest 컨텍스트만 띄움, 예: `node dist/batch.js cleanup-tmp-images`) — OS cron·컨테이너 크론잡·수동 실행용, 실무의 "배치 프로세스"에 가장 가까움
- 외부 호출용 HTTP 엔드포인트는 만들지 않는다 → Q4는 위 구조로 정리.
- 중복 실행(배포 중 인스턴스 2개): 삭제가 멱등이라 문제는 없다. 학습 목적이면 락·실행 이력 테이블을 둘 수 있다. 단 Postgres 세션 락은 pooler 모드에 따라 동작이 다르므로 그때 검토한다.
- Render의 별도 크론잡 서비스는 제가 알기로 유료 — 확인 필요.

### 9-2. 표지 교체·제거 시 기존 이미지 처리 (사용자 제안, 가능)
| 상황 | 처리 | 이유 |
|---|---|---|
| 저장 **전**에 올린 A를 B로 교체(둘 다 tmp) | 바로 삭제 가능. 삭제 API는 `tmp/reading/<본인>/` 키만 허용 | 아직 어디에도 저장 안 됨. 저장된 파일은 이 API로 못 지움 |
| **저장된** 표지(`reading/…`)를 교체·제거 | 저장 **성공 후 서버가** 옛 파일 삭제 | 클릭 시점에 지우면, 수정하다 취소했을 때 DB는 옛 파일을 가리키는데 파일이 없어짐 |
| 기록 삭제(`remove`) | DB 삭제 후 표지 삭제 | 같은 이유 |
- 원칙: **저장된 파일은 FE가 직접 지우지 못하게 하고, 저장 성공 후 서버가 지운다.**
- 순서: 새 파일 승격 → DB 갱신 → 옛 파일 삭제(최선). 삭제가 실패해도 기록은 정상이고, 남은 파일은 주기적 대조(5절)로 정리한다.
- **확인할 것**: "표지 제거"를 서버에 어떻게 알리는가. `coverImageUrl`이 DTO에서 `@IsOptional() @IsString()`이라 빈 문자열인지 `null`인지 정해야 하고, FE가 지금 무엇을 보내는지는 아직 확인하지 않았다.

### 9-3. 표지 제거 시 FE가 보내는 값 (확인함)
- 표지 삭제 버튼은 `setCoverImageUrl("")`로 **빈 문자열**을 만들고, 저장·자동저장은 매번 `coverImageUrl`을 페이로드에 **항상 포함**해서 보낸다(`WriteReadingLogForm.tsx`).
- BE `UpdateReadingLogDto`는 `@IsOptional() @IsString()`이라 `""`도 통과하고, 서비스가 `...fields`로 그대로 DB에 쓴다 → **표지 없음이 `null`이 아니라 빈 문자열 `""`로 저장된다.** 타입은 `string | null`이고 FE는 읽을 때 `?? ""`로 합친다.
- 구현 시: `""`와 `null`을 모두 "표지 없음"으로 취급해야 한다(참조 대조·옛 파일 삭제 판단 포함).
- FE에서 `coverImageUrl`을 **채우는 곳은 업로드 결과(`result.url`)와 저장된 값 불러오기뿐**이다. 카카오 검색 등 외부 URL로 채우는 경로는 없다. 발행된 독서 기록은 현재 0건(2026-10-13 확인).

### 9-4. 사용자 답변 (2026-10-13)
- **Q1**: 임시저장은 tmp에 유지한다. 나중에 임시저장한 글·독서·컨텐츠도 배치가 모두 정리하게 한다.
  - 검토: draft가 tmp 이미지를 **참조한 채 오래 살 수 있어서**, "tmp 파일 나이"만으로 지우면 살아 있는 draft의 이미지가 깨진다. → 배치는 **참조 여부를 DB로 확인**하고, 오래된 draft 자체도 정리(보관 기간 N일 필요)해야 한다. 영구 폴더로 옮기는 시점은 자동저장이 아니라 **발행(`publish: true`) 때**로 단순해진다.
- **Q2**: 의미 설명 필요 → 아래 질문에서 답변(표지를 우리 R2 주소로만 허용할지).
- **Q3**: 사용자가 내일 준비(도메인 확인).
- **Q5**: 배치 없이 보관 기간으로 삭제할 수 있는지 문의 → R2 수명주기 규칙으로 가능(제가 알기로, 확인 필요). 단 파일 나이만 보므로 Q1의 draft 참조와 충돌 → 안전망 용도.
- **Q6**: 아직 고려하지 못함.
- **Q7**: "키"가 무엇인지 문의 → R2 파일 경로 문자열(`reading/<userId>/<uuid>.png`)을 뜻한다고 설명.

## 10. 확정한 방향 (2026-10-13)

### 10-1. 배치 규칙 — 하나로 통일
> **R2 파일 중, DB 어디에서도 참조하지 않고, 마지막 수정 후 24시간이 지난 것을 삭제한다.** (`tmp/`와 `reading/` 모두)

- 이 규칙 하나로 정리되는 것: 저장하지 않고 나간 업로드, 교체·제거된 옛 표지, 삭제된 기록의 표지, 회원 탈퇴(cascade)로 남은 파일.
- 24시간 유예는 아직 저장 전인 새 업로드를 보호한다.
- 참조 여부는 **모든 `ReadingLog` 행**(draft·발행 모두)의 `coverImageUrl`을 기준으로 본다. `""`와 `null`은 "참조 없음".
- 이벤트 때 바로 지우는 로직(교체·제거·삭제 직후 삭제)은 **필수가 아니다.** 나중에 더하는 최적화로 둔다.
- 폴더는 계속 나눈다: `tmp/reading/<userId>/<uuid>.<ext>`(발행 전) → `reading/<userId>/<uuid>.<ext>`(발행 후, **발행 시 복사 후 삭제**로 승격). 폴더를 나누면 운영 중 눈으로 보기 쉽고 R2 수명주기 규칙(안전망)을 `tmp/`에만 걸 수 있다.

### 10-2. 표지 URL은 우리 R2 주소만 허용 (Q2 확정)
- `coverImageUrl`은 우리 R2 공개 주소의 `tmp/reading/<본인>/…` 또는 `reading/<본인>/…`만 허용하고, 그 밖의 값은 400으로 거절한다. 빈 문자열("표지 없음")은 허용.
- 본인 폴더인지 검사한다(남의 파일을 자기 기록에 가져오는 것 방지).
- 지금 FE는 업로드 결과로만 값을 채우므로 기존 흐름에 영향이 없다. 기존에 저장된 `uploads/…` 값이 있다면 어떻게 취급할지는 구현 때 확인한다(발행된 기록은 2026-10-13 기준 0건).

### 10-3. draft는 내용과 함께 배치가 삭제 (사용자 결정)
- 임시저장(draft)된 글·독서 등 **모든 콘텐츠를 그 이미지와 함께** 배치가 정리한다. 이미지만 따로 남기지 않는다.
- 실행 순서: ① 보관 기간이 지난 draft 삭제 → ② 그 결과 참조가 사라진 이미지를 10-1 규칙으로 삭제. (순서가 반대면 방금 지운 draft의 이미지가 다음 실행까지 남는다.)
- **아직 미정: draft 보관 기간(N일).** 기준 시각은 생성일이 아니라 **마지막 수정일(`updatedAt`)** 이어야 한다(오래 쓰는 중인 draft를 지우지 않으려면).
- 주의: 사용자의 작성 중인 내용을 영구 삭제하는 일이라 되돌릴 수 없다. N을 넉넉하게 잡고, 삭제 건수를 로그에 남긴다. 범위는 우선 독서만이고, 글(`Post`)의 draft 정리는 글 이미지 단계에서 같이 정한다.

### 10-4. 배치 실행 방식
- 작업 본체는 HTTP와 무관한 서비스로 만들고, 앱 안의 `@Cron`(시간대 `Asia/Seoul`, 새벽 3시)과 독립 실행 스크립트 두 방식으로 붙인다(9-1). cron-job.org에는 의존하지 않는다.

### 10-6. 구현 순서 (프로젝트 규칙, 승인 후)
1. API 계약 합의: 업로드 API의 종류(`kind=reading`)와 저장 위치, `coverImageUrl` 검증 규칙
2. FE: MSW·유닛 테스트 (업로드는 tmp, 발행 때만 영구 폴더)
3. BE: 테스트 목록·골격은 Claude, 케이스 작성은 사용자. 업로드(tmp), 발행 시 승격(복사 후 삭제), 검증, 배치(draft 정리 → 참조 없는 파일 삭제)
4. 통합 확인: 로컬에서 로그인 후 업로드 → 임시저장 → 발행 → 배치 실행
- 시험 중 올린 파일은 운영과 같은 R2 버킷에 있다. 현재 `uploads/…`에 남은 시험 파일은 수동 정리 대상.
